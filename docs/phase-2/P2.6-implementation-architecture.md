## 3. Selected Technology Stack

Every selection is traced to an accepted requirement or invariant. Alternatives and reversibility are in the Technical Decision Log (§23); this section states the choices and the one-line reason.

| Layer | Selection | One-line reason |
|---|---|---|
| **Language / runtime** | **TypeScript on Node.js** (strict compiler settings), one codebase for core application + worker; the Assistant is a separate TypeScript service | Three processes must share the Context API, outbox event, and domain-type contracts — one language halves contract-maintenance cost; mature streaming-LLM tooling for the Assistant; fastest path to a running local system (R20). **This is the most reversible choice and may be overridden at P2.7 with rationale** (each process is a typed network contract). |
| **Primary datastore** | **PostgreSQL** (single logical instance) | Transactional integrity for the atomic write set (INV-8, P2.5 §12.4); native full-text search *inside the system of record* so indexes stay transactionally consistent with their source text (INV-6); recursive CTEs for the 2-hop assembly (P2.5 §13.2); `FOR UPDATE SKIP LOCKED` gives an in-database job queue and outbox poller with no broker (INV-13); `JSONB` for the mutable-type attribute bag (R21) alongside typed columns for everything that drives authorization, ranking, or provenance (INV-2, INV-5); self-hostable, cheap, one-container local dev. |
| **Lexical search** | **PostgreSQL full-text search** (`tsvector` + GIN) plus a worker-maintained **distinctive-term table** | Keeps retrieval in the SoT — no second system to run, no index-lag class beyond what P2.5 §12.5 already accepts, and the visibility predicate composes *into* the search query so `filter → assemble → rank` holds natively (the §13.3 anti-pattern is structurally avoided). |
| **Async / worker** | **In-database job queue + transactional outbox** (`SELECT … FOR UPDATE SKIP LOCKED`) | The outbox row is written in the same transaction as the mutation — no dual-write, at-least-once is natural (INV-13); correct and observable at A1 scale; a broker would be unjustified infrastructure (P2.5 §17). |
| **Inter-process (Assistant ↔ Core)** | **Internal HTTP/JSON** — the Context API — over a private network, service-token auth carrying the end-user principal per request | Request/response shape fits HTTP; debuggable; contract-testable; the Assistant's own client streaming is a separate concern. |
| **Data access** | **Typed SQL query builder** (no heavy ORM); **versioned plain-SQL forward-only migrations** | The `VisibilityPolicy` must compose into *every* read as a predicate (P2.5 §15.4); an ORM's implicit joins and lazy loading fight that and risk an unprincipled query path (INV-3). Explicit SQL keeps the schema reviewable and INV-6's "documented rebuild" honest. |
| **Testing** | Stack test runner + **property-based testing** library + ephemeral PostgreSQL (containerised) + **import-boundary / architecture linter** + contract-conformance suites | The invariants need property tests (no-side-channel), architecture tests (INV-1/2/14), and provider-conformance suites — not just unit tests. |
| **LLM provider** | **Deferred.** `LLMProvider` interface + a `FakeLLMProvider` default for dev/test | Not needed to specify the foundation; keeps INV-7 and §15 provider-agnostic. Selection is a P2.7 input. |
| **Local dev** | `docker compose` with **PostgreSQL only** + three Node processes + deterministic seed + `FakeLLMProvider` | R20: the whole system on one machine, one database, seeded data, no external API key required to work on the core. |
| **Deployment** | Three containers + one PostgreSQL, two network zones; any container host | The minimum topology that realises the accepted process and trust boundaries with no distributed-systems overhead. |

**Not selected, deliberately:** frontend framework, HTTP framework specifics, hosting platform, CI system, cloud provider, message broker, vector store, external search engine, graph database, authentication provider. None is required to make the foundation implementation-ready; each is a later choice constrained by the contracts here.

## 5. Runtime Boundaries

| Component | Runs as | Responsibilities | Must NOT |
|---|---|---|---|
| **Core application** | Node process, Zone A, stateless, horizontally replicable | Workspace CRUD-with-semantics, confirmed writes, suggestion intake, the Context Engine, the single `VisibilityPolicy`, the Context API server | Generate natural language; make outbound internet calls; expose a read path without a principal |
| **Context Engine** | A module inside the core process (not a separate deployable) | Candidate gathering, structural-edge computation, dedupe, layering, per-layer caps, ranking with versioned weights, factor traces, provenance attachment, typed failure results | Hold conversation state; call external services; skip the filter-first step |
| **Authorization** | A module inside the core process | Produce the visibility predicate in both forms (SQL fragment + in-memory function) from one rule source; deny by default | Live in the Assistant; live in an index; be bypassable by any repository method |
| **RetrievalProvider** | An interface with one MVP implementation (`LexicalRetrievalProvider`) inside the core process | Return principal-scope-restricted similarity candidates; provide a documented `rebuild` | Return a global top-K that the caller must filter afterwards |
| **Worker** | Node process, Zone A, same codebase as core, different entrypoint | Drain the outbox; generate candidates under an owner-scoped principal; maintain derived indexes; roll up telemetry; sweep staleness | Serve an interactive request; emit a Context Set to a person; run as a superuser |
| **Assistant service** | Node process, Zone B, separate deployable, separate credentials | Resolve intent, reason over Context Sets, draft proposals, hold conversation state, talk to the external model | Hold datastore credentials; reach PostgreSQL; write authoritative data; supply or elevate a principal |
| **External model boundary** | The `LLMProvider` call from Zone B | Receive only a principal-filtered Context Set plus the user's question, on explicit invocation | Receive corpus-wide data, other principals' data, or anything from a background job |
| **PostgreSQL** | One logical instance, Zone A | The single system of record; host the derived indexes; back the job queue and outbox | Be reachable from Zone B |
| **Derived lexical indexes** | Tables/columns in PostgreSQL, written only by the worker | Speed the content signal; be fully rebuildable from authoritative rows | Ever be consulted for authorization; ever be the source of an explicit relationship |
| **Outbox** | `outbox_event` table + a worker poller | Carry domain events to consumers at-least-once, written in the mutation's transaction | Be written outside the mutation transaction; assume exactly-once delivery |

## 6. Internal Module Boundaries

Enforced by an import-boundary linter (architecture test). Direction of allowed dependency is strictly inward.

```
  domain/            pure. objects, relationships, confidence, provenance, visibility-scope
                     value objects; VisibilityPolicy rules; ContextSet + ContextSetRequest
                     shapes; ranking factor model. NO i/o, NO sql, NO http, NO framework.
     ▲
  application/        use cases: capture, confirmed-write, assemble-context-set, handoff,
                     suggestion lifecycle. orchestrates domain + ports. NO sql, NO http.
     ▲
  ports/             interfaces only: ObjectRepository, RelationshipRepository,
                     SuggestionRepository, SuppressionRepository, UsageSignalRepository,
                     RetrievalProvider, OutboxWriter, AuditLog, Clock, RankingWeights.
                     every read method takes `principal` as a required parameter.
     ▲
  adapters/
    persistence/     THE thin, explicitly-labelled persistence layer (INV-14).
                     the ONLY place SQL lives. the ONLY place storage-shaped tests live.
                     composes VisibilityPolicy into every query.
    http/            core HTTP API + the Context API server.
    retrieval/       LexicalRetrievalProvider (Postgres FTS). + InMemoryRetrievalProvider
                     (reference second impl, test-only, keeps INV-11/INV-14 honest).
  worker/            entrypoint + job handlers. imports domain/ application/ ports/
                     adapters/persistence/. registers outbox consumers.
  assistant/         SEPARATE DEPLOYABLE. intent, reasoning, proposals, conversation store,
                     LLMProvider port + FakeLLMProvider. depends on a Context API *client*.
                     MUST NOT import adapters/persistence/ or the database driver — checked.
```

Rules the linter enforces:
- `domain/` imports nothing outward; no `pg`/driver, no `http`, no framework.
- `application/` imports `domain/` and `ports/` only.
- The database driver is imported only within `adapters/persistence/`.
- `RetrievalProvider` is referenced by `application/` only through `ports/`; no `application/` file names an index or a query (INV-1).
- `assistant/` has no dependency edge to `adapters/persistence/` or the driver (INV-4) — verified in its build graph.
- Tests outside `adapters/persistence/` assert against the Context API / port contracts, not SQL (INV-14); a lint rule flags storage-shaped assertions elsewhere.

## 7. Authoritative Data Model

Implementation-level model. **Not DDL and not a migration** — column lists are the shape the schema must express. Classification per row set: **A** = authoritative persisted, **D** = derived (rebuildable, never authoritative), **R** = runtime-only (never persisted).

### 7.1 Authoritative (A)

| Store | Shape (columns) | Notes |
|---|---|---|
| `workspace` | id, created_at | The tenancy scope carried everywhere (P2.5 §16). |
| `principal` | id, workspace_id, auth_subject (opaque), created_at | The identity a request runs as. Authentication *mechanism* deferred (P2.7); the record and `auth_subject` link exist now. |
| `workspace_membership` | workspace_id, principal_id, role (`member` for MVP), joined_at | Presence = belongs to the workspace. Roles beyond `member` deferred. |
| `object` | id, workspace_id, **type** (mutable), title, body, **attributes** (JSONB), home_project_id (**nullable** → Inbox), **owner_id (NOT NULL, defaults to creator)**, created_by (immutable), created_at, updated_at | One identity space, mutable type (R21). `title`/`body` are typed columns because they feed FTS; `attributes` holds type-varying fields so re-typing is a field update, not a table move (P2.5 §12.1). **`owner_id` is NOT NULL on every object type** — see §9.2: the visibility predicate's ownership clause is the *only* thing that makes an Inbox object (no home Project) visible to anyone, so a nullable owner would render every unfiled capture invisible to its own creator. `owner_id` is the transferable ownership that handoff changes (Task/Project); `created_by` is immutable authorship and is never rewritten by sharing or handoff (R8). For types that have no product-level notion of ownership, `owner_id` simply stays at the creator. |
| `object_contributor` | object_id, principal_id, first_contributed_at | Authorship survives sharing/handoff (R8). |
| `relationship` | id (surrogate), workspace_id, from_object_id, to_object_id, **verb**, **origin** (`explicit` \| `user_confirmed`), author_id, created_at, **visibility_scope** (`shared` \| `private`), provenance_kind, provenance_actor_id, provenance_detail (typed) | First-class edge with its own identity and lifecycle (INV-2). **Only `explicit` and `user_confirmed` origins are stored here** — see §8.3 for why `structural` is computed, not stored. |
| `relationship_suggestion` | id, workspace_id, from_object_id, to_object_id, proposed_verb, **confidence_state** (`known` \| `user_confirmed` \| `inferred_high` \| `weak`), signals (typed columns/rows, not a blob), generated_at, generated_by (worker run id), owner_scope_id | Family 2 (P2.5 §12.3). Worker-only writes. Freely discarded and rebuilt. `owner_scope_id` records which owner-scoped principal produced it (§9.6). |
| `relationship_suppression` | workspace_id, from_object_id, to_object_id, verb, suppressed_by, suppressed_at | Family 3. **Always reapplied** after any recompute (R4). |
| `usage_signal` | workspace_id, principal_id, object_id, kind (`pin` \| `dismiss` \| `open`), at | Family 3, per-user. |
| `activity` | id, object_id, workspace_id, kind, actor_id, at, detail (JSONB) | Append-only (R22). Backs the MVP flat activity list; a timeline later needs no remodel. |
| `audit_event` | id, workspace_id, actor_id, action, at, originating_conversation_id (nullable), supporting_refs (JSONB of ids) | Append-only, its own schema namespace (R15, P2.5 §12.6). References, not payloads. |
| `outbox_event` | id, workspace_id, type, payload (JSONB), created_at, delivered_at (nullable), attempts, dead_lettered (bool) | Written in the mutation's transaction (INV-13). |
| `project_share` | workspace_id, project_id, principal_id, granted_by, granted_at | Drives visibility. **Zero rows = fully functional solo system** (INV-12). |
| `ranking_weight_set` | version (string), weights (JSONB), activated_at | Versioned; exactly one active (INV-10). |
| `telemetry_event` | id, workspace_id, kind, refs (JSONB of ids), at | Append-only. **Identifiers/outcomes only, never object content** (R23, P2.5 §15.8). Carries the G1–G4 gate counters (P2.5 §13.4). |

**JSONB governance for `object.attributes`** — three rules so it does not become a way to avoid domain decisions:
1. **Nothing in `attributes` may participate in authorization.** Every field the visibility predicate reads (`workspace_id`, `owner_id`, `home_project_id`) is a typed column. A JSONB key is never consulted for access control.
2. **Fields that feed retrieval or ranking are declared**, not discovered: the FTS projection uses a **versioned whitelist** of `attributes` keys (§12), and anything that drives ranking or explanation is a typed column, not a blob (INV-5, INV-10 — P2.5 §12.2's "provenance is typed, not a free-form blob").
3. **Each object type has a validated attribute schema** enforced at the application layer, versioned alongside the type. `attributes` is a *typed-per-type* bag whose shape is known and checked — it exists to make re-typing cheap (R21), not to postpone modelling. A field that every type carries belongs in a column.

## 8. Relationship Model

The most consequential part of the foundation (INV-2, and the 1:1 graph-edge mapping that keeps A→C cheap — P2.5 §18).

### 8.1 First-class edges
`relationship` has a **surrogate id** and an **independent lifecycle**: a relationship can be created, user-confirmed, re-typed, removed, or superseded without any write to either endpoint object. It carries `verb`, direction (`from`/`to`), `author_id`, `created_at`, typed `provenance_*`, `confidence_state` (for the authoritative table this is `known` or `user_confirmed`), and its own `visibility_scope`. This is the structure a future derived graph projection ETLs directly (INV-11).

### 8.2 The `belongs to` carve-out (INV-2) — two targets, two storage forms

P2.1 §8 gives `belongs to` **two distinct uses**, and they cannot share one storage form:

| Use | Target | Storage | Why |
|---|---|---|---|
| **Home context** — "every non-Project object has exactly one home Project, or sits in the Inbox" (P2.1 §5) | **Project** | `object.home_project_id` (nullable FK) | Singular by definition; the FK is the integrity constraint. This is the carve-out P2.5 INV-2 sanctions ("stored on the object for integrity"). |
| **Anchor to the active work item** — "any capture → active work item (the **Task or Project** currently in focus)" (P2.1 §3, §7, §8); and a Checkpoint is "a snapshot **on a Task or Project**" (P2.1 §2) | **Task** or Project | a real `relationship` row, `verb = belongs_to`, `origin = explicit`, written in the capture transaction | A foreign key on `object` cannot express a Task target. Storing it as a real edge is the INV-2-compliant form. |

**This distinction was missing from the first draft of P2.6, which stored `belongs to` only as `home_project_id`.** That model could not represent a Checkpoint anchored to a Task — which is the backbone of the Work Context (P2.1 §2, §6) and therefore of I1 Resume and of the first vertical slice P2.5 §23 specifies. The correction is above.

Rules:
- At most one **anchor** edge per object; enforced by a partial unique constraint on `(from_object_id)` where `verb = belongs_to`. "Singular" (P2.1 §8) is preserved per use, not collapsed across the two uses.
- An object may simultaneously have a home Project (IA/navigation) and an anchor to a Task (capture context). These are not in conflict: a Checkpoint anchored to Task T also has T's home Project as its own.
- `RelationshipRepository.forObject(principal, objectId)` returns real `relationship` rows **unioned with** a synthesised `belongs_to` edge derived from `home_project_id`, so no consumer special-cases the foreign key (INV-2).
- Anchor edges are authoritative and immediate (R3) — they are `explicit`, not inferred, and never recomputed.

### 8.3 Structural *signals* vs. relationship *storage* — a distinction the first draft collapsed

P2.2 §2's "structural signals" is a **scoring category**, not a storage class. Some of those signals are read from stored authoritative edges; only some are derivable from object fields. The first draft of P2.6 treated all of them as computable, which was wrong for three of them.

**Computed on read** (derivable from object fields; never persisted; rebuilt every assembly):
- co-membership in the same home Project;
- same owner / same creator;
- Task state adjacency;
- co-membership in one assembled Work Context.

**Stored as authoritative `relationship` rows** (user- or system-asserted facts that cannot be derived from fields):
- `supersedes` — a user assertion about two Decisions (P2.1 §8 verb);
- `derived from` — including Idea→Task promotion lineage (P2.1 §8 verb; promotion is deferred per P2.1 §9, but when it lands it writes this edge);
- `belongs_to` **anchor** edges (§8.2);
- every other user-authored verb.

Consequences:
- **`origin` domain:** the authoritative `relationship` table stores `explicit` and `user_confirmed` only. There is no persisted `structural` origin — computed structural edges are materialised into the read model at query time and carry `confidence_state = known` with a **synthetic, non-persisted provenance** naming the rule that produced them (INV-5).
- **C2 separation stays trivial:** dropping and rebuilding `relationship_suggestion` touches nothing authoritative.
- **Latency fallback:** if 2-hop assembly latency (A3) is breached, the computed set can be materialised as a derived (D) table behind the same read-model interface — no contract change (§25, Q2).

### 8.4 Confidence
`confidence_state` has four values (P2.2 §4). Authoritative `relationship` rows are `known` (structural, when surfaced) or `user_confirmed`. `inferred_high` and `weak` exist only on `relationship_suggestion` rows. Promotion `weak/inferred_high → user_confirmed` is a user-confirmed write that inserts a `relationship` row and may delete the suggestion; it re-validates both endpoints inside the transaction (P2.5 §12.5).

### 8.5 Visibility scope on the edge (R9a)
`visibility_scope ∈ {shared, private}`. A `private` relationship is visible only to `author_id`, even when both endpoints are visible to others — this is the R9a defect fix. The **default value** for a user-created link is a product-policy decision, not decided here (§25, Q1); the *representation* and the *enforcement* (§9.3) are decided.

### 8.6 The 10-verb vocabulary
Enumerated by P2.1 §8. P2.7 must restate the exact list for the schema `verb` domain (§24). Inverse relationships are computed for display, never stored twice (P2.5 §12.2).

## 9. Authorization Model

The authoritative enforcement mechanism. Designed so unauthorised retrieval is structurally impossible, not prompt-dependent.

### 9.1 Principal
`Principal = { id, workspaceId }`. **Always** derived from an authenticated end-user credential; **never** from a request body or a client-controlled header (INV-4a). There is no service-level principal that can stand in for a user. How the Assistant conveys the end-user principal without being able to assert one is specified in §14.1 — a service token authenticates the *caller*, never the *user*.

### 9.2 The single `VisibilityPolicy`
One module in `domain/` is the only expression of the predicate (P2.5 §15.2, §15.4). It emits **two forms from one rule source**:
1. a **SQL predicate fragment** parameterised by the resolved scope, composed into every `adapters/persistence` read (the filter-first path, INV-3);
2. a **pure function** `canSee(scope, objectOrRelationship): boolean` for post-hoc checks on `RetrievalProvider` hits and any derived datum (P2.5 §15.5).
A cross-check test asserts the two forms agree over generated inputs.

**Both forms consume one per-request `ResolvedScope` snapshot.** The scope — principal id, workspace id, and the set of project ids shared with that principal — is resolved **once, at the start of a request**, and every subsequent read in that request uses that same snapshot. Without this, the SQL form and the `canSee` form can read `project_share` at different instants and disagree mid-request when a share changes concurrently, producing an inconsistent Context Set (and, in the worst ordering, an item admitted by one form and cited by the other). A single snapshot makes each request internally consistent; the next request picks up the change (§9.7 revocation).

```
visible(object, s)  ⟺  object.workspace_id = s.workspaceId
                       ∧ ( object.owner_id = s.principalId
                           ∨ object.home_project_id ∈ s.sharedProjectIds )
                       -- Inbox object (home_project_id IS NULL) ⇒ owner-only,
                       -- which is why object.owner_id is NOT NULL (§7.1)

visible(rel, s)     ⟺  visible(from(rel), s) ∧ visible(to(rel), s)
                       ∧ ( rel.visibility_scope = 'shared' ∨ rel.author_id = s.principalId )
```
Conjunctive, deny-by-default. Unknown/unlabelled scope ⇒ invisible.

**Why `owner_id` must be NOT NULL (a correctness dependency, not a style choice):** the ownership clause is the *only* disjunct that can admit an Inbox object, since its `home_project_id` is NULL. The first draft of P2.6 made `owner_id` nullable for non-Task/Project types, which would have made every unfiled capture invisible to its own creator — and the tempting "fix" of falling back to workspace-wide visibility would have been a privacy leak. §7.1 now fixes `owner_id` NOT NULL, defaulted to the creator.

**Computed structural edges** have no stored `author_id` or `visibility_scope`. They are derived *only* from an already-filtered object set, so `visible(from) ∧ visible(to)` holds by construction and the edge clause is not applicable — they are treated as `shared` within that filtered set and can never widen it.

### 9.3 Enforcement points
| Surface | How authorization is applied |
|---|---|
| Object read | SQL fragment composed into the query; no repository method without a `principal` parameter. |
| Relationship read | SQL fragment includes both endpoint checks **and** the edge `visibility_scope`/`author` clause (R9a). |
| Structural edges (computed) | Computed only from already-filtered objects, so they inherit visibility by construction. |
| Retrieval filtering | The `RetrievalProvider` receives the resolved visible scope and returns only in-scope ids; results are additionally re-checked with `canSee` before assembly (defence in depth, P2.5 §13.3 / §15.5). |
| Index filtering | Index hits are candidates only; the authoritative predicate runs before anything is emitted; index membership is never permission (INV-6). |
| Worker scope | Owner-scoped synthetic principal (§9.6); never a superuser; candidate rows spanning what no single principal can see together are never written. |
| Assistant scope | Receives only what the Context API emits for its propagated end-user principal; cannot request another principal or widen scope (INV-4). |
| External AI egress | Only the already-filtered `ContextSet` for that principal, on explicit user invocation (INV-7). |

### 9.4 Ordering (INV-3)
`filter → assemble → rank`, always. Per-layer caps, counts, "N more" indicators, and handoff completeness are computed **only** over the filtered set. Filtering after ranking is forbidden (it leaks existence through position/count — R9 no-side-channel).

### 9.5 Structural guarantee, not a convention
- Every `ports` read method's signature makes `principal` required; there is no overload without it — omission is a compile error.
- Constructing a persistence query outside the policy-composing helper is blocked by an architecture-lint rule.
- The core zone has no outbound internet route (network policy), so no code path — buggy or not — can exfiltrate.
- The Assistant build graph contains no database driver (checked), so it has no query path at all.

### 9.6 Worker principal (owner-scoped inference, P2.5 §15.9.1, INV-3)
For candidate generation the worker synthesises, per owner, a principal representing **that owner's visible set** and computes candidates within it. It never proposes a relationship whose endpoints no single principal can see together. The worker has no interactive response path and emits no `ContextSet` to a person. Handoff dual-principal evaluation (§10.7) is the only other non-interactive predicate evaluation, and it may only *narrow* the requester's own visible set.

### 9.7 Revocation (P2.5 §15.10)
- Interactive reads are correct on the **next** assembly — a direct consequence of assemble-on-read / no cache (ADR-8).
- Unsharing or narrowing a scope **enqueues** an outbox event that triggers candidate + index recompute; until it runs, stale derived data is harmless because read-time filtering is authoritative (INV-6).
- Conversation history is re-scoped **going forward, not retroactively** (P2.3 §11) — content already delivered into a conversation before revocation stays in that conversation. This is an accepted, inherited limitation, not an MVP feature gap (§25, Q6).
- Telemetry/audit hold identifiers only — nothing to revoke.
- A handoff whose `ContextSet` was computed before revocation is **re-evaluated at acceptance**, not delivered from the earlier evaluation.

## 10. Context Engine Contract

An in-process module in the core application, exposed to the Assistant over the Context API (HTTP/JSON).

### 10.1 Request
```
ContextSetRequest {
  principal:  Principal                 // from auth context, not the body (INV-4a)
  purpose:    'resume' | 'decision_recall' | 'handoff'
  target:     ObjectRef                 // MVP: an object id. topic targets are a later extension.
  scope?: {
    timeWindow?:       Duration         // defaults to the configured work-session window
    projectScoped?:    boolean
    handoffRecipient?: PrincipalRef      // required when purpose = 'handoff'
  }
  limits?: { perLayerCaps?: Partial<Record<Layer, number>> }   // defaults from config
}
```

### 10.2 Result — `Ok(ContextSet)` or `Unavailable(reason)`
```
ContextSet {
  weightSetVersion: string                       // INV-10
  layersPresent:    Layer[]
  items:            ContextItem[]                 // ranked, deduped to strongest path, capped
  completeness?:    HandoffCompleteness           // purpose = 'handoff' only
  generatedAt:      Timestamp
  staleness?:       { latestCheckpointAgeSeconds } // R18, when a Checkpoint is in scope
}
ContextItem {
  object:           ObjectSummary                 // id, type, title, owner, timestamps, home project
  viaRelationships: RelationshipRef[]             // typed; each with confidence_state + provenance
  layer:            'direct' | 'recent' | 'high_confidence' | 'indirect' | 'historical' | 'potential'
  rank:             number
  factorTrace:      RankingFactor[]               // INV-10: which factors placed it, and their weights
  provenance:       Provenance                    // INV-5: cites only refs the principal can already see
}
```
`Layer = 'direct' | 'indirect' | 'recent' | 'historical' | 'high_confidence' | 'potential'` (P2.2 §6). Default emission: `high_confidence ∩ (direct ∪ recent)`; `indirect` / `historical` / `potential` only when the request asks (P2.2 §6, §10).

### 10.3 Failure behaviour (R16, P2.5 §14)
`Unavailable(reason)` is a distinct result from an empty `ContextSet`. The Assistant maps `Unavailable` to "retrieval failed, retry?" and must not substitute model priors or history. Callers may request **one** additional set per turn; no unbounded looping.

### 10.4 Pipeline order (INV-3, non-negotiable)
resolve `ResolvedScope` (§9.2) → compose `VisibilityPolicy` predicate → filtered candidate query (explicit edges + suggestion rows admitted by confidence + lexical hits, all pre-filtered) → compute structural edges over the filtered object set → dedupe to strongest path → assign layers → apply per-layer caps → rank with the active `ranking_weight_set` → attach factor traces + provenance (re-checked with `canSee`) → return. No step operates on unfiltered data.

**Traversal (the recursive CTE) — rules that must hold, not just at the seed:**
- **Visibility is composed into the recursive term, not only the anchor term.** Filtering the seed and then expanding freely would pull invisible objects in at hop 2. Every expansion step re-applies the object *and* relationship predicates of §9.2.
- **Depth is enforced in the query** by an explicit depth counter (`depth < 2`), not merely by convention — the cap is a domain-contract parameter (§22), passed in, not hardcoded.
- **Cycles** are bounded by the depth cap, but a visited-set (path array) is still carried so a cycle cannot produce repeated expansion work.
- **Duplicate paths** to the same object are expected and collapsed by the dedupe step, which keeps the **strongest** path (highest-provenance relationship, then shortest depth) and records the others in `viaRelationships` so provenance is not lost (INV-5).
- The traversal returns object ids plus path metadata only; object bodies are fetched in a second, equally-filtered read.

### 10.5 Ranking (INV-10)
Factors (P2.2 §7): provenance (`user_confirmed`/`known` > `inferred_high` > `weak`), purpose-relevant verb, recency, status, project relevance, temporal proximity, usage signal. Weights come from the one active `ranking_weight_set`; the version and a per-item factor trace are in every `ContextSet`.

**Determinism requires a total order.** Same inputs + same `weightSetVersion` ⇒ **identical** ranked output — which holds only if ties are broken deterministically. The sort key is `(score DESC, layer_priority ASC, object.created_at ASC, object.id ASC)`; the final `object.id` term guarantees totality. Ranking is performed in application code over the filtered, assembled set (not by relying on any database's unordered result), so the golden-file test in §17 asserts a genuinely reproducible artefact rather than an incidentally stable one.

### 10.6 Limits
Per-layer caps from config (values are a P2.7 input — §24). Context Sets are bounded, so there is **no user-facing pagination** in MVP.

### 10.7 Handoff
`purpose = 'handoff'` computes the set under the **recipient's prospective post-acceptance scope**, intersected with the sender's own visible set (so it can reveal nothing new about the recipient). `HandoffCompleteness` lists gaps; sender-private residue is reported to the sender as an "additional private context exists" flag only — never its content, never to the recipient (P2.5 §15.7).

## 11. RetrievalProvider Contract

The seam that makes lexical → hybrid → semantic a swap of implementation and nothing else (P2.5 §13.3, INV-1).

```
// Storage-neutral by construction: NO sql fragment, NO query object, NO driver type.
// An external provider must be able to consume this without knowing the datastore.
type ResolvedScope = {
  workspaceId:       WorkspaceId
  principalId:       PrincipalId
  sharedProjectIds:  ProjectId[]          // resolved once per request (§9.2)
}

interface RetrievalProvider {
  // MUST return only object ids the given visibility scope admits.
  findSimilar(input: {
    scope:      ResolvedScope             // the caller's per-request snapshot
    queryText:  string
    k:          number
  }): Promise<Array<{ objectId: ObjectId; score: number; evidence: TermEvidence[] }>>

  // INV-6: documented, runnable rebuild from authoritative rows.
  rebuild(workspaceId: WorkspaceId): Promise<void>

  describe(): { kind: 'lexical' | 'hybrid' | 'semantic'; version: string }
}
```

**`ResolvedScope` is deliberately storage-neutral.** The first draft left it undefined, which risked it becoming a SQL predicate fragment — convenient for the in-database lexical provider and *unusable* by any external one, quietly making the seam un-swappable and defeating its whole purpose. It is therefore plain data. An in-store provider may additionally accept an opaque optimisation hint (e.g. a pre-built predicate) **only** as a private extension that no interface consumer may depend on, and never as a substitute for the plain-data scope.

Binding eligibility rules (from P2.5 §13.3):
1. The provider **receives the visibility scope and must pre-restrict** its results to it. A provider that can only return a global top-K is **ineligible** unless it also offers a documented, measured over-fetch strategy with a stated recall guarantee.
2. `score` is opaque and **never enters the `ContextSet` contract** — it is one input to the engine ranker, nothing more.
3. `evidence` is provider-shaped and optional to consumers.
4. Swapping providers changes only `adapters/retrieval/` and its wiring. `domain/`, `application/`, the `ContextSet` contract, and the Assistant contract are untouched.

A second implementation, `InMemoryRetrievalProvider`, exists in the test suite and is kept green — this is what makes INV-11 concrete and INV-14's "reference derived consumer" real.

## 12. Lexical Search Architecture

MVP retrieval. No embeddings, no vector store (P2.5 Q1).

| Concern | Decision |
|---|---|
| **Searchable fields** | `object.title`, `object.body`, and a **whitelisted** projection of `attributes` keys (e.g. a Decision's rationale text). The whitelist is config, versioned with the index. |
| **Distinctive terms** | A tokenizer that keeps `.`/`/`/`_`/`-`-joined tokens whole (file paths, identifiers, error strings, library names — P2.2 §2). Extracted terms populate `distinctive_term` with per-workspace `document_frequency`. Exact tokenizer rules need a small spec + corpus (§25, Q5). |
| **Indexing strategy** | `object_fts.fts` is a `tsvector` maintained by the worker on `object` change events (via the outbox); GIN index on it. `distinctive_term` frequencies recomputed by the worker. Both are **derived (D)** and rebuildable. |
| **Visibility enforcement** | The FTS match is expressed **inside** the principal-filtered query: `WHERE object_fts.fts @@ to_tsquery(:q) AND <VisibilityPolicy SQL fragment>`. Filter-first holds natively — this is the specific reason in-database FTS was chosen over an external engine. |
| **Ranking** | `ts_rank` contributes **one factor** to the Context Engine ranker (the content-signal factor). It is never the sole ranker; final ordering is the engine's, with versioned weights (INV-10). |
| **Pagination / limits** | The lexical candidate query is `LIMIT k`, where `k` is a configured multiple of the largest per-layer cap (headroom for dedupe/re-rank). Context Sets themselves are capped and not paginated. |
| **Stale-index handling** | Index lag on the *content signal* is acceptable (P2.5 §12.5); explicit relationships never come from the index (INV-6), so R3 immediacy is unaffected. Where staleness touches a Checkpoint it is surfaced (R18). |
| **Deletion** | Deleting an object: the authoritative transaction removes the object and its `relationship` rows and writes an outbox event; the worker then removes the `object_fts` row and decrements `distinctive_term` frequencies. History retains the prior existence of the removed relationships (P2.5 §12.6). |
| **Reindex** | `LexicalRetrievalProvider.rebuild(workspaceId)` truncates and repopulates `object_fts` and `distinctive_term` from authoritative `object` rows. Documented and runnable on demand (INV-6). The `attributes` FTS whitelist is **versioned**; changing it bumps the version and requires a rebuild, so index contents always correspond to a known whitelist version. |

### 12.1 Making G1–G4 actually measurable (the condition on lexical-only MVP)

P2.5 §13.4 accepted lexical-only retrieval **conditionally** on these gates. A gate that cannot be computed is not a condition — it is a hope. The first draft named the gates but did not specify the events they need, and G1 in particular was **not computable**: it asks whether a pair was surfaced as a candidate *before* the user manually linked it, yet `relationship_suggestion` rows are "freely recomputed, expired, and discarded" (§7.1), so the historical fact would already be gone. Required telemetry (identifiers and outcomes only, never content — §7.1 `telemetry_event`, R23):

| Event | Emitted when | Fields | Gate served |
|---|---|---|---|
| `suggestion_surfaced` | a candidate is included in an emitted `ContextSet` or suggestion list | workspace, principal, from/to object ids, verb, confidence_state, contributing signal kinds, weight-set version | **G1** (was the pair ever surfaced?), **G2** (did the content signal contribute?) |
| `relationship_manually_created` | a user authors a link by hand | workspace, principal, from/to, verb, and whether a prior `suggestion_surfaced` exists for that pair | **G1** (the false-negative numerator) |
| `context_set_emitted` | every assembly | purpose, item count per layer, weight-set version, latency, whether the target was named explicitly | **G3**, **G4** denominators |
| `context_item_acted_on` | the user opens, pins, or acts on an item from a set | set ref, item rank, layer, provenance class | **G4** (first-acted position), **G3** (was the correct Decision present?) |

`suggestion_surfaced` is what makes G1 computable **without** retaining discarded suggestion rows: the surfacing fact is recorded when it happens, so the later manual link can be joined against it. These four events ship with the first vertical slice; thresholds are calibrated later (P2.5 §13.4).

## 13. Worker Architecture

| Concern | Decision |
|---|---|
| **Responsibilities** | (a) drain the outbox; (b) candidate generation (owner-scoped); (c) `object_fts` + `distinctive_term` maintenance; (d) telemetry roll-up incl. the G1–G4 counters; (e) staleness sweeps. |
| **Job model** | Poll `outbox_event` (and, if needed, a `worker_job` table) with `SELECT … FOR UPDATE SKIP LOCKED`; a claimed row has a lease. Each handler is a function of its input + the same repositories the core uses. |
| **Transaction boundaries** | A handler claims a row, does its work, and commits derived writes **plus** the "delivered"/"done" marker in **one transaction**. A crash before commit ⇒ the lease expires ⇒ redelivery. |
| **Authorization context** | An **owner-scoped synthetic principal** per owner (§9.6). Never a superuser. No `ContextSet` is ever produced for a person by the worker. **The owner scope is resolved at *execution* time, never captured at enqueue time** — a job queued before a share was revoked must run under the scope as it stands when the handler runs, or revocation would be silently bypassed by the backlog (§9.7). |
| **Idempotency & convergence** | Handlers are **state-based**: given "object X changed", read X's current authoritative row and recompute the derived state (§16). This makes redelivery, retry, out-of-order delivery, and concurrent workers converge. |
| **Retry semantics** | Bounded attempts with exponential backoff; `attempts` incremented per try; after N, the event is `dead_lettered` and a metric fires — the queue is not blocked. |
| **Idempotency** | Every handler keyed by `(event_id, handler_name)`; redelivery converges (INV-13). FTS upserts and frequency recomputes-from-source are naturally idempotent. |
| **Failure handling** | Worker down ⇒ candidates and indexes go stale while explicit + structural signals keep working; the system degrades to a smaller but correct `ContextSet`, visibly (R18), never silently (P2.5 §12.5). |
| **Outbox interaction** | The worker is *the* outbox consumer host; consumers register by event type; an unknown event type is logged and skipped, not fatal. |
| **Derived-index interaction** | Only the worker writes `object_fts` and `distinctive_term`. The request path only reads them. |
| **Instances** | One worker instance is sufficient for A1. `SKIP LOCKED` makes N instances safe if ever needed (§25, Q4). |

## 14. Assistant Architecture

| Concern | Decision |
|---|---|
| **Process boundary** | Separate deployable, separate container, **Zone B**. No database credentials, no database route, no ambient datastore access (INV-4). Its build graph contains no DB driver — checked in CI. |
| **Context access** | Only via a Context API **client**, forwarding the end user's own credential on every call — see §14.1. Receives `Ok(ContextSet)` or `Unavailable`. |
| **Mutation authority** | None. The Assistant may only `POST` to the core's **suggestion** endpoint, which creates `relationship_suggestion` rows (never authoritative) that require later user confirmation (INV-8). No tool grants the model a write. |
| **Untrusted output / input** | Model output is a structured, validated, **inert** proposal until a user confirms. Shared/ingested content in the prompt is data, never instruction. |
| **Conversation store** | The Assistant's own schema with its own credential; never read by the core as workspace context (R14). Cross-device sync deferred. |
| **Provider** | `LLMProvider` interface; `FakeLLMProvider` is the default in dev/test; a commercial provider is a P2.7 selection. |
| **Engine independence** | The core system is fully functional with the Assistant absent (R11) — guaranteed by it being a separate deployable with a one-way dependency. |

### 14.1 Context API authentication — how INV-4a is actually enforced

The first draft said the Assistant "passes the end-user `Principal` on every call" while §9.1 said a principal is never taken from a client-controlled field. For the Context API the Assistant **is** the client, so those two statements were in conflict, and as written the Assistant would have been asserting the user's identity under its own service token — a textbook confused deputy, and INV-4a ("the Assistant cannot supply, substitute, or elevate a principal") would have been unenforceable. Resolved as follows:

- **Two independent credentials per call, with different jobs.**
  1. A **service token** identifies the *caller* (the Assistant service) and authorises it to reach the Context API surface at all. It conveys **no user identity**.
  2. A **forwarded end-user credential** — the same short-lived, audience-restricted token the user's own session presents to the core — conveys *who the request is for*. The core **validates it itself** and derives `Principal` from it. The Assistant never constructs, mints, or mutates it; it only relays what the user's request arrived with.
- **The core derives the principal solely from (2).** It never reads a principal id from a body field, a path parameter, or an Assistant-set header. A call presenting only a service token is rejected — there is no user to act for.
- **The forwarded credential is audience-restricted** to the Context API, so a leaked one cannot be replayed against the core's general write API.
- **Consequence:** the Assistant cannot request another user's context, because it holds no credential for another user. Its reach is exactly the set of users who are actively talking to it, for the duration of their own tokens.
- **Testable (INV-4a):** service-token-only calls rejected; body/header-supplied principal ignored; a token for user A cannot yield user B's Context Set; an expired forwarded credential fails closed.

If a deployment cannot forward end-user credentials, the alternative is a core-issued, per-request, single-use delegation token minted **by the core** at the start of a user turn — never a principal asserted by the Assistant. That variant is a P2.7 implementation choice; the invariant it must satisfy is fixed here.

### 14.2 What the process boundary protects — and does not (P2.5 §4.Q2, verbatim intent)
- **Protects (the one property):** no code path in the component that talks to an external model can read the datastore directly or via ambient credentials. A coding error in the Assistant cannot assemble unfiltered context and send it outward, because it has **no path to the database**. Enforced at runtime by process + network + credential isolation, not by convention.
- **Does NOT protect against — covered elsewhere:**
  - **Prompt injection** — bounded entirely by INV-8 (proposals are inert; no write tool). A separate process does not make manipulated output safer.
  - **Principal-propagation errors** — if the Assistant calls the Context API with the wrong principal, isolation does not help; INV-4a plus its own end-to-end test is the control.
  - **Write safety** — already fully bounded by confirm-before-write; it is *not* a reason for the boundary.
- **Accepted costs:** one extra deployable; a versioned inter-process contract; cross-process debugging and tracing; per-turn latency; a second thing to run locally.

## 15. External AI Boundary

| Question | Answer |
|---|---|
| **What may leave the trust boundary** | Only the content of a `ContextSet` already filtered for the invoking principal, plus that user's question. Nothing else — no corpus-wide data, no other principals' data, nothing from a background job (INV-7). |
| **Who authorises egress** | The end user, by explicitly invoking the Assistant. There is no background or engine-initiated egress. |
| **How context is minimised** | The `ContextSet` is already bounded by per-layer caps; the Assistant sends only the items relevant to the resolved intent. A redaction/consent point exists at this boundary (its UX is deferred — P2.5 §22). |
| **When the external model is unavailable** | Report the failure and offer retry; never substitute priors or conversation history (R16). At most one retry of a single additional `ContextSet` request per turn. |
| **Secret isolation** | The model API key exists **only** in Zone B. Zone A holds no such secret and has no outbound route. The Context API service token is issued to Zone B and scoped to the Context API surface only. |
| **What is logged** | Request id, principal id (not name), purpose, item count, model id, latency, token counts, outcome. **Not** the content sent. An opt-in, separately access-controlled, retention-bounded debug sink may capture an assembled set for diagnosis; off by default. |

## 16. Transactional Outbox

| Concern | Decision |
|---|---|
| **Event creation** | An `outbox_event` row is `INSERT`ed **in the same transaction** as the authoritative mutation (the atomic set: object + `belongs_to` + `activity` + `audit_event` + `outbox_event` — P2.5 §12.4). No dual write. |
| **Delivery semantics** | At-least-once (INV-13). A worker poller reads undelivered rows oldest-first with `SKIP LOCKED`, dispatches to registered consumers, marks `delivered_at` on success. |
| **Idempotency** | Consumers are keyed by `(event_id, handler_name)` and must converge on redelivery, restart, or replay. No consumer may assume exactly-once. |
| **Ordering — what the outbox does NOT guarantee** | **No ordering guarantee is claimed or relied upon.** With `SKIP LOCKED` and any retry, events for the same object can be processed out of order — so an "object updated" event retried after an "object deleted" event could otherwise resurrect a deleted index row. The rule that removes this class entirely: **every consumer is state-based, not delta-based.** A handler receives an event as a *hint that object X changed*, then reads X's **current authoritative row** and recomputes the derived state (absent row ⇒ delete the derived row). Handlers never apply a payload delta. Under this rule, out-of-order and duplicate delivery converge to the same result, and multi-instance workers stay safe. Event payloads therefore carry identifiers and a change kind, never denormalised content. |
| **Retry behaviour** | Per-row `attempts` + backoff; after N attempts the row is `dead_lettered` with a metric; the queue continues. |
| **Failure recovery** | On restart the poller resumes from undelivered rows; nothing is lost because the event was committed with the write. |
| **Consumers (MVP)** | candidate-generation, fts-maintenance, distinctive-term-maintenance, telemetry-rollup, staleness-sweep. Registered by event type; unknown types logged and skipped. |
| **Evolution hook** | Consumer registration is an interface — a message broker or a derived-graph-projection consumer can be added behind it **without changing producers** (P2.5 §18). |

### 16.1 System failure matrix

Behaviour that implementation must not invent (extends P2.5 §12.5, which this section does not restate).

| Failure | Behaviour |
|---|---|
| **Database unavailable** | Core returns a typed failure; the Context API returns `Unavailable` (not `Empty`) so the Assistant reports retrieval failure and offers retry (R16). No degraded read path exists — there is nothing correct to serve without the system of record. |
| **Context API unavailable / timeout** | Assistant maps it to `Unavailable`; never substitutes model priors or conversation history (R16, INV-7). Core and worker are unaffected — the dependency is one-way. |
| **Lexical index unavailable or corrupt** | The content signal degrades to absent; explicit, structural, temporal and usage signals still assemble a correct, smaller Context Set (P2.2 §10 sparse-data behaviour). `rebuild()` restores it. Authorization is never affected — the index was never authoritative (INV-6). |
| **Worker down** | Candidates and indexes go stale; explicit and structural signals keep working; staleness is surfaced (R18), never silent (P2.5 §12.5). |
| **Outbox backlog / poller stalled** | `outbox lag` metric fires (§20). Derived state is stale but authoritative reads are unaffected. Convergence on resume is guaranteed by state-based consumers (§16). |
| **Assistant down** | The core system is fully functional (R11) — the workspace, engine and all confirmed writes are unaffected. |
| **External model unavailable** | Report and offer retry; never fabricate (R16). The already-assembled Context Set is still shown to the user by the core UI path. |
| **Partial write** | Impossible for the atomic set (§12.4 of P2.5): object + `belongs to` + activity + audit + outbox commit together or not at all. |
| **Concurrent edit / concurrent confirmation** | Per P2.5 §12.5: last-write-wins at field level with activity preserving the change; confirmation re-validates endpoints inside the transaction. |
| **Visibility change during queued work** | The job resolves owner scope at execution time (§13), so it runs under post-change visibility. |

| **Worker scope** (§9.6) | Property test: no `relationship_suggestion` row has endpoints that no single principal can see together. |
| **RetrievalProvider contract** (§11) | A conformance suite run against *every* provider implementation (lexical + in-memory reference), including the scoped-result eligibility rule. |
| **Revocation** (§9.7) | Property test: after unshare, the next assembly excludes the now-invisible items; candidates/indexes converge after the enqueued recompute; a handoff computed pre-revocation is re-evaluated at acceptance; **a worker job enqueued before the revocation runs under the post-revocation scope** (execution-time resolution, §13). |
| **Scope-snapshot consistency** (§9.2) | Test that both `VisibilityPolicy` forms consume the same per-request `ResolvedScope`, and that a share change committed mid-request does not alter that request's result. |
| **Traversal** (§10.4) | Property test: no object beyond depth 2 appears; visibility holds at **every** hop (an object reachable only via an invisible intermediate is absent); cycles terminate; duplicate paths collapse to the strongest while `viaRelationships` retains the alternatives. |
| **Ranking determinism** (§10.5) | Shuffle input order and re-rank: output must be byte-identical, proving the tiebreak is total. |
| **Outbox convergence** (§16) | Deliver events out of order and duplicated (incl. update-after-delete): derived state converges to the state-based result; no resurrected index rows. |
| **G1–G4 measurability** (§12.1) | Assert the four telemetry events are emitted with the fields the gates need, and that G1 is computable from `suggestion_surfaced` alone without retaining discarded suggestion rows. |
| **G1–G4 gates** (P2.5 §13.4) | The counters exist and are emitted from the first slice; a test that the gate events are recorded on manual-link creation, decision-recall interactions, and first-acted-item selection. |

Support: ephemeral PostgreSQL (containerised) for integration; a deterministic seed; contract tests for the Context API shared by the core (server) and the Assistant (client).

Minimum setup to run the **complete** system on one machine (R20):

1. `docker compose up` → **one** container: PostgreSQL. (Nothing else is required infrastructure.)
2. Three Node processes, run directly or in compose: `dev:core`, `dev:worker`, `dev:assistant`.

## 19. Deployment Architecture

Minimum production topology. The architecture contains process boundaries; it is **not** a distributed system and must not be built as one.

- **Containers:** 3 — core API, worker, assistant. **Datastore:** 1 PostgreSQL (managed or self-run).
- **Zone A** (core API + worker + PostgreSQL): **no outbound internet route**. Holds DB credentials and user-auth secrets.
- **Zone B** (assistant): outbound to the model provider only; **no route to PostgreSQL**. Holds the model API key and the Context API service token.
- **Cross-zone:** Zone B → Zone A over a private network, Context API only.
- **Scaling:** core API is stateless → replicate freely behind a load balancer. One worker instance suffices for A1 (multiple are safe via `SKIP LOCKED` if ever needed). PostgreSQL vertical + a read replica if measured load requires — deferred (P2.5 §17).
- **Not required:** Kubernetes, service mesh, message broker, autoscaling, multi-region. Any container runtime works.
- **Deferred to implementation:** the specific container host, CI system, TLS termination, and secret manager.

## 21. Security Model

| Boundary | Statement |
|---|---|
| **Trust zones** | Zone A (core + worker + DB, no egress); Zone B (assistant, egress to model only, no DB route). The browser/client is untrusted. |
| **Credential ownership** | DB credentials → Zone A only. User-auth secrets → Zone A only. Model API key → Zone B only. Context API service token → issued to Zone B, scoped to the Context API surface. |
| **Network / process boundaries** | Zone B → Zone A: private network, Context API only. Zone A → internet: blocked. Zone B → PostgreSQL: no route. Assistant build: no DB driver. |
| **Authorization enforcement** | The single `VisibilityPolicy`, composed into every read, filter-first (INV-3). No unprincipled repository method (compile-time). |
| **Data-flow boundaries** | Authoritative writes only via the confirmed-write path in Zone A. Derived data written only by the worker. Content leaves the system only as a principal-filtered `ContextSet`, only via the Assistant, only on explicit user invocation. |
| **External egress** | Zone B → model provider only; logged as metadata (no content) by default. |
| **Principal integrity** | Always from the authenticated request context; never from a client-controlled field; no service principal substitutes for a user (INV-4a). |

## 22. Evolution / Migration Hooks

Interfaces and structures that must remain stable so future capability is *additive*, not a rewrite (P2.5 §18). **None of these future systems is built now.**

| Must stay stable | Enables |
|---|---|
| `ContextSetRequest` / `ContextSet` (the Context API contract) | Any change to assembly internals, ranking, or retrieval without touching the Assistant. |
| `RetrievalProvider` interface + the scoped-result eligibility rule (§11) | lexical → hybrid → semantic as a provider swap; `pgvector` in the same PostgreSQL is the smallest next step. |
| The outbox **consumer-registration** interface | A derived graph projection, an external search engine, or a broker added as a new consumer without changing producers. |
| `RelationshipRepository` **edge-shaped** read model (incl. synthesised `belongs_to`) | A future graph projection ETLs `relationship` rows 1:1; no consumer special-cases the foreign key. |
| The `relationship` table's edge shape (id, from, to, verb, origin, author, visibility_scope, typed provenance) | The 1:1 graph-edge mapping that keeps A→C an ETL, not a redesign (INV-2, INV-11). |
| `VisibilityPolicy` dual form (SQL fragment + `canSee` function) | Applying authorization to a new store (projection/index) reuses the in-memory form; no re-derivation. |
| `Principal` shape | Stable identity across a future process split along the Context API. |
| The 2-hop cap expressed as a **domain-contract parameter**, not a hardcoded constant | Raising traversal depth later is a config + query change, inherited by any future engine. |

Additional integrations (Phase 4): new `object.type` values (the mutable-type + `attributes` model already allows this) + a new outbox **producer** / ingest worker feeding `relationship_suggestion` and `usage_signal`. Additive (R19).

**Canonical export (INV-9 — a design goal, not a requirement).** Because all authoritative data (§7.1) lives in one relational store with an edge-shaped `relationship` table and typed provenance, a documented dump of objects + relationships + provenance + activity + audit in an open format stays cheaply producible. It is retained as insurance and **must not be used to constrain schema evolution** — exactly as P2.5 INV-9 states.

## Consistency with prior milestones

**Review corrections applied (P2.6 implementation-architecture review, pre-acceptance).** The selected architecture and every P2.5 invariant are unchanged; no P2.5 reopening was required. Three blocking defects and six material gaps in the first draft were closed:

*Blocking:* (1) **`belongs to` could not target a Task.** The draft stored it solely as `object.home_project_id`, but P2.1 §3/§8 attach every capture to the *active work item — a Task or Project*, and P2.1 §2 anchors a Checkpoint to a Task. The draft therefore could not represent the Checkpoint→Task anchor that the Work Context (P2.1 §2, §6), I1 Resume, and the first vertical slice (P2.5 §23) are built on. §8.2 now defines two storage forms for the verb's two uses. (2) **The visibility predicate depended on a nullable `owner_id`.** Since an Inbox object has no home Project, the ownership disjunct is the only one that can admit it — so a nullable owner made every unfiled capture invisible to its own creator, and the tempting fix would have been a workspace-wide leak. §7.1 makes `owner_id` NOT NULL, defaulted to the creator, with `created_by` remaining immutable authorship. (3) **The Context API's principal handling was a confused deputy.** The draft had the Assistant "passing the end-user Principal" while §9.1 forbade taking a principal from a client-controlled field — as written, INV-4a was unenforceable. §14.1 now specifies two independent credentials: a service token that authenticates the *caller* only, plus a forwarded, audience-restricted end-user credential that the core validates itself.

*Material:* (4) **Structural signals vs. relationship storage were conflated** — `supersedes`, `derived from`/lineage and Checkpoint anchoring are user- or system-asserted edges that must be *stored*, not computed from object fields; §8.3 now separates the two. (5) **No per-request scope snapshot** — the SQL and `canSee` forms could read `project_share` at different instants and disagree mid-request; §9.2 fixes one `ResolvedScope` per request. (6) **Traversal rules were unstated** — visibility must be composed into the *recursive* term, not only the seed, with an in-query depth cap, cycle handling and strongest-path dedupe (§10.4). (7) **`ResolvedScope` was undefined** and risked becoming a SQL fragment, which would have made the retrieval seam unusable by any external provider; §11 fixes it as storage-neutral plain data. (8) **The outbox implied ordering it cannot provide** — an update retried after a delete could resurrect an index row; §16 now requires **state-based, not delta-based** consumers, and §13 resolves worker owner-scope at execution time so a queued job cannot bypass a revocation. (9) **G1 was not computable** — suggestion rows are freely discarded, so the "was this pair ever surfaced?" fact would already be gone; §12.1 adds the four telemetry events that make P2.5's acceptance condition measurable. Also added: a deterministic total sort order so INV-10's golden-file claim is real (§10.5), JSONB governance rules (§7.1), a system failure matrix (§16.1), and six new invariant tests (§17).

No contradictions with P1.1, P1.2, P2.1, P2.2, P2.3, P2.4, or P2.5. This document adds no product scope, changes no object model or vocabulary, and alters no P2.5 boundary or invariant. It selects concrete technologies (permitted at this milestone) and defines contracts, all traced to accepted requirements and invariants. Where P2.5 §22 left decisions open, this document either resolves them at the implementation-foundation level (structural-edge computation, data-access approach, local/deploy topology) or carries them forward as §24 inputs / §25 questions.
