# P2.2 — Context Engine

Architecture/product-system design. Defines **how contextual relationships are discovered, evaluated, maintained, and surfaced** inside the Personal Developer Workspace (P2.1). Not an implementation. No technology, database, embedding/model provider, API, auth, or integration choices. The AI Assistant is defined here **only** as a boundary (P2.3 owns it).

Context: `Claude_Project_Blueprint.md`, `docs/phase-1/P1.1-problem-definition.md`, `docs/phase-1/P1.2-individual-small-team-scope.md`, `docs/phase-2/P2.1-personal-developer-workspace.md`.

Builds on P2.1's object model (Project, Task, Note, Idea, Decision, Resource, Checkpoint; derived **Work Context** view), P2.1's 10 typed relationship verbs, and P2.1's privacy model (private by default, explicit Project-level sharing, handoff). **No contradiction with P2.1 was found** — P2.1 §8/§9 explicitly deferred automatic relationship suggestion and inference to this document (see §"Consistency with P2.1").

---

## 1. Context Engine Purpose

**Problem it solves.** In P2.1 the relationship graph is only as complete as the links a developer manually creates. Developers under-link (P1.1). So connected context stays partly mental and the reconstruction cost persists. The engine fills the graph with *candidate* relationships and surfaces the *right bounded subset* of context around whatever the developer is looking at — so the graph grows and stays useful without manual curation.

**Responsible for:**
- Discovering candidate relationships between existing workspace objects.
- Scoring each inferred relationship's confidence.
- Maintaining the relationship lifecycle (re-scoring, withdrawal, honoring user decisions).
- Assembling bounded, ranked **Context Sets** around an object for a stated purpose (resume, decision-recall, handoff).
- Enforcing visibility on everything it outputs.

**Not responsible for:**
- Creating or editing workspace objects (the user does, per P2.1).
- Deciding that a relationship is *true* — inferred links are probabilistic; the user confirms.
- Any natural language: answers, summaries, explanations in prose, recommendations, generated next actions (P2.3).
- External data ingestion (Phase 4).
- Storage, graph representation, retrieval technology (§14).

**Four layers — keep distinct:**

| Layer | What it is | Standing |
|---|---|---|
| Workspace data | Objects and their fields, user-authored | Authoritative fact |
| Relationships | Typed links (P2.1 §8) | Authoritative **if** user-authored/confirmed; probabilistic **if** engine-inferred |
| Context Engine inference | Candidate relationships + confidence + Context Sets + ranking | Probabilistic, explainable, reversible; never overrides the user |
| AI Assistant reasoning | Language and recommendations built from Context Sets | Consumer of the above; not a relationship store (P2.3) |

**Support for the priority workflows:**
- **I1 (resume interrupted work):** assembles and ranks the Task's Context Set for the Resume view (latest Checkpoint, blockers, next action, relevant Decisions/Notes), so the developer reads rather than manually reassembles across tools.
- **I3 (decision recall):** surfaces Decisions relevant to a Task or topic via `explains`/`caused by` plus content/temporal signals, even when the user never linked them.
- **T1 (developer handoff):** produces a handoff Context Set, visibility-filtered to the recipient, with a completeness check that flags likely-missing context to the sender.

## 2. Context Sources

Only signals derivable from P2.1 objects and in-workspace activity. **No external integrations.**

| Category | Examples (over P2.1 objects) | Weight |
|---|---|---|
| **Explicit user relationships** | The 10 typed verbs authored or confirmed by a user; one hop from such a link | Authoritative — highest |
| **Structural signals** | Shared home Project; `belongs to` chains; Checkpoint anchored to its Task/Project; Idea→Task promotion lineage; Decision `supersedes` chain; same owner/creator; co-membership in one assembled Work Context; Task state | Strong |
| **Temporal / contextual signals** | Created or edited close in time; captured while the same "active work item" was in focus (P2.1 §7); co-opened in one Resume session; recency of activity | Weak alone, strong as corroboration |
| **Content / semantic signals** | Text similarity between titles/bodies; shared *distinctive* terms treated as workspace-internal entities/topics (file paths, error strings, library names, ticket-like tokens); a Decision's subject matching a Task body | Weak alone, strong when corroborated |
| **Usage signals** | What context the user pinned, opened repeatedly, or dismissed for a given object; manual link created just after viewing a suggestion | Adjusts ranking and future confidence; per-user, never shared |

Entity/topic extraction is a **workspace-internal index**, not an external knowledge base; technique and provider are unspecified (§14).

## 3. Relationship Discovery

For a target object the engine produces ranked **candidate relationships**. Conceptual pipeline (order is not a technology commitment):

1. **Candidate generation** — collect objects sharing any signal with the target: same home Project; within a temporal-proximity window; content similarity above a floor; ≥1 shared distinctive entity; one hop from an existing explicit relationship; Decisions whose subject overlaps the target.
2. **Candidate typing** — propose a verb from the signal pattern:
   - Structural facts → their exact verb directly (`belongs to`, `supersedes`, promotion → `derived from`).
   - Decision semantically about a Task + temporally near → `explains` (candidate).
   - Task created right after a Decision → `caused by` (candidate).
   - Two Tasks sharing entities, one already `blocked` → `blocked by` (low-confidence candidate).
   - Generic similarity only → `related to`.
3. **Scoring** — combine evidence into a confidence state (§4).
4. **Filtering** — drop below-threshold candidates, duplicates (§10), and anything that violates visibility (§11).
5. **Output** — ranked candidates for human confirmation (§8) and inclusion in Context Sets by confidence (§6).

**Combination principle:** no single weak signal (content similarity alone, temporal proximity alone) yields a *surfaced* relationship. Corroboration across ≥2 independent signal categories is required to surface an inferred link. Explicit relationships and strong structural signals may stand alone.

No AI/ML provider or technique is committed here (§14).

---

## 4. Relationship Confidence

**Four states the system must distinguish:**

| State | Basis | Surfacing |
|---|---|---|
| **Known / structural** | A workspace fact (shared Project, Checkpoint anchor, supersede chain, promotion lineage) | Always shown; no confirmation; treated as true |
| **User-confirmed** | User authored it or accepted a suggestion | Authoritative; same standing as Known; never auto-removed |
| **Inferred — high confidence** | ≥2 corroborating categories **including** a strong signal (explicit-link adjacency, strong structural overlap, or high content similarity + shared distinctive entity) | Shown in context, labelled *inferred*; may be offered for one-click confirmation |
| **Weak / possible** | Single signal, or weak corroboration only | **Not** in the primary context view; available only via an on-demand "possibly related" area; never used for handoff completeness |

**Strong evidence:** an explicit user relationship or one hop from it; shared home Project + a shared distinctive entity; Checkpoint / promotion / supersede structure; high content similarity co-occurring with temporal proximity in the same work session.

**Weak evidence:** content similarity alone; temporal proximity alone; a shared common (non-distinctive) term; same author alone.

**Rules:**
- Known + User-confirmed → always surfaced (subject to §11).
- Inferred-high → surfaced, visually marked, optionally offered for confirmation.
- Weak → hidden from primary context; on demand only.
- **User confirmation is required** before an inferred relationship is treated as authoritative, before it may affect Task `blocked by` semantics, or before it counts toward handoff completeness.
- Every inferred relationship carries its state label and can show which signals produced it. The engine never presents an inferred link as a plain fact (**no false certainty**).
- Conservative default: borderline evidence resolves to **Weak**, not Inferred-high.

## 5. Relationship Lifecycle

**Persistence model: hybrid.** Inferred candidates are **recalculated** as inputs change; the **user's decisions** about them (accept / reject) and **usage feedback** are **persisted** and always reapplied.

| Event | Engine behavior |
|---|---|
| First inferred | Stored as a candidate: state (Inferred/Weak), timestamp, contributing signals. Surfaced per §4. |
| User accepts | Becomes **User-confirmed**; persisted; removed from recalculation churn; now acts as a strong signal for further discovery. |
| User rejects | Persisted as a **suppression** for that pair+type. Not re-surfaced unless materially stronger new evidence appears — and then only as a fresh low-priority suggestion, never a silent reinstatement. |
| New nearby information | Affected candidates re-scored; confidence may rise or fall. A surfaced inferred link that drops below threshold is quietly withdrawn from primary context (not deleted if user-confirmed). |
| Object edited | Its content/entity signals recomputed; candidates involving it re-evaluated incrementally. |
| Object deleted | All relationships to it removed; dependent inferred context recalculated. The link's prior existence may remain in history/activity per P2.1. |
| Decision superseded | Context weighting shifts to the superseding Decision; the superseded one is demoted in ranking but stays discoverable (P2.1 §3); inferred `explains` links become candidates re-pointed to the new Decision (user-confirmable). |
| Task changes state | Ranking recomputed (done Tasks fall in a Resume Set; `blocked by` targets rise). Relationships are not deleted. |
| Context becomes stale | Staleness flagged in the assembled context (P2.1 §6); time-sensitive signals down-weighted. The engine does not fabricate freshness. |

Inferred relationships are therefore **both** recalculated **and** backed by persisted user decisions; user-authored relationships are purely persistent.

---

## 6. Context Assembly

For a target object the engine builds a **Context Set**: layered, bounded, ranked.

**Layers:**
- **Direct context** — one Known/explicit hop away: current Checkpoint, `explains` Decisions, `blocked by` Tasks, `references` Resources, home Project.
- **Indirect context** — two Known/explicit hops, or one Inferred-high hop.
- **Recent context** — recent shared activity or same-work-session capture, regardless of link type.
- **Historical context** — older related objects (prior Checkpoints, superseded Decisions, completed preceding Tasks); collapsed by default.
- **High-confidence context** — the Known + User-confirmed + Inferred-high subset; the default visible set.
- **Potential context** — Weak/possible; excluded by default, reached via an explicit "explore related" action.

**Anti-flood rules:**
- Each layer has a bounded item count; default view = High-confidence ∩ (Direct ∪ Recent).
- Indirect / Historical / Potential are on demand.
- Information reachable by several paths is deduplicated to one entry citing its strongest path.
- The Set is a ranked list (§7), never an exhaustive dump. **Useful context over maximum context.**

**Purpose-scoped assembly:**
- **Resume (I1)** — favors current Checkpoint, next action, blockers, unresolved open questions.
- **Decision-recall (I3)** — favors Decisions and their `caused by` / `explains` neighbors.
- **Handoff (T1)** — favors everything a new owner needs; runs a completeness check (§10, §13) and applies the recipient visibility filter (§11).

---

## 7. Context Ranking

**Factors (applied within a Context Set):**
- **Provenance:** User-confirmed / Known > Inferred-high > Weak (Weak excluded by default).
- **Relationship-type relevance to purpose:** Resume → `next action for`, `blocked by`, `explains` outrank `related to`; Decision-recall → `caused by`, `explains` outrank others.
- **Recency** of activity on the related object.
- **Status:** target and related object status (open/blocking rises; done/superseded falls).
- **Project relevance:** same home Project > linked cross-Project > weakly related other Project.
- **Temporal proximity** to the target's active work.
- **Usage/history:** previously pinned or repeatedly opened rises; previously dismissed falls.

**Conflict resolution:**
- Provenance dominates: a User-confirmed `related to` outranks an Inferred-high `explains` for a contested slot.
- Provenance tie → purpose-relevance of the type, then recency.
- Contradictory signals (e.g. high similarity but user previously dismissed) → the **user decision wins**; item demoted or hidden.
- One object surfacing via multiple relationships is ranked by its strongest and annotated with the others.
- Ranking is **deterministic given its inputs and explainable** (which factors placed an item where), so HITL corrections are meaningful.

## 8. Human-in-the-Loop Behavior

All controls are reversible.

| Control | Effect |
|---|---|
| Accept suggestion | Relationship → User-confirmed |
| Reject suggestion | Persisted suppression for that pair+type (§5) |
| Correct relationship type | Re-typed, becomes User-confirmed with the corrected verb; the signal→type mapping is treated as wrong for this case |
| Manually create relationship | Authoritative; uses P2.1 vocabulary |
| Remove relationship | User-authored/confirmed links removable; removal persisted and not casually re-inferred |
| Pin context | Forces an object into the target's default Context Set at top rank, regardless of engine score |
| Mark context irrelevant / dismiss | Removes it from this target's Set; lowers that pairing globally |
| Explore related | Opens the Potential/Weak layer for manual promotion |

**Principles:** no inferred relationship is irreversible; every automatic action is visible, labelled, and undoable; the engine never deletes user-authored structure; a suggestion becomes authoritative only by explicit user action.

---

## 9. Context Engine vs AI Assistant

| | **Context Engine (P2.2)** | **AI Assistant (P2.3)** |
|---|---|---|
| Job | Discover candidate relationships; score confidence; maintain lifecycle; assemble bounded, ranked, visibility-safe Context Sets | Reason over the engine's Context Sets to answer questions, summarize, explain decisions in prose, propose next actions, draft tasks from notes |
| Output | Structured sets of objects + relationships + confidence + provenance | Natural language and recommendations |
| Nature | Deterministic, explainable | Generative, non-deterministic |
| Relationship store | Owns candidate + confirmed inferred structure | Owns none; any connection it notices must go through the same HITL suggestion path — it cannot write authoritative relationships |
| Dependency | Runs and delivers value with **no** AI Assistant present | Depends on the engine for its context input |

**Why the split:** the engine must reduce reconstruction even with no AI; the AI must not be the sole holder of how context connects (single point of failure, non-deterministic, harder to keep private). The AI is a **consumer** and a **suggestion source**, never the system of record for relationships or ranking. This document does not design the AI Assistant beyond this boundary.

## 10. Failure Modes

| Failure | Detection | Desired behavior |
|---|---|---|
| **False relationship** (false positive) | User rejects/dismisses a surfaced inferred link | It was labelled inferred and confirmable; one reject suppresses it; never auto-promoted; Weak links kept out of primary view to bound this. Track correction rate (§13). |
| **Missing relationship** (false negative) | Manual link created between two objects the engine held but didn't surface | Manual linking always cheap (P2.1); "explore related" exposes Weak candidates; handoff completeness check flags unlinked objects sharing the work session/Project. |
| **Stale context** | Latest Checkpoint old; related objects inactive | Staleness flagged; time-sensitive signals down-weighted; stale objects demoted, not hidden; "last updated N ago" shown. |
| **Excessive relationships** | An object linked to many others | Ranking + per-layer caps; show top-N with "more"; prefer relationship-type diversity over many `related to`. |
| **Context overload** | Assembled Set too large | Default view = High-confidence ∩ (Direct ∪ Recent), bounded; rest on demand; purpose-scoped assembly. |
| **Incorrect confidence** | User corrects a link's standing | Confidence is explainable (signals listed); correction adjusts this pairing and the contributing signal weights; conservative default (borderline → Weak). |
| **Duplicate relationships** | Same pair+type from multiple signals or user + engine | Dedupe to one; user-authored supersedes inferred of the same pair+type; Set shows one entry. |
| **Contradictory information** | Conflicting Decisions; signal vs prior user decision | Engine does not adjudicate content truth; surfaces both linked Decisions with timestamps and supersede status; user decision beats signal. |
| **Ambiguous entities** | Same term/different meaning, or same concept/different terms | Entity match alone is Weak unless corroborated (shared Project/time); never the sole basis for a surfaced link; user can split/merge a topic via correction. |
| **Sparse workspace data** | Few objects/links to infer from | Degrade to structural + explicit only; no fabricated inferred links; communicate "context grows as you capture" (principle 6 — improves with accumulation, not manual organization). |

## 11. Privacy / Visibility Boundaries

Honors P2.1 (private by default, explicit Project-level sharing).

- The engine computes and outputs relationships **per the viewer's visible scope**. An object a user cannot see never appears in that user's Context Set.
- Inference over private data runs **for that owner only**. Sharing a Project does not share inferred results unless **both endpoints** of the relationship are inside the shared scope.
- **Cross-Project relationship:** shown to a viewer only if the viewer can see **both** endpoints. If one endpoint is out of scope, the relationship and every hint of the hidden object (title, snippet, existence, "related item you can't see") are omitted entirely.
- **Shared Project:** teammates get context assembled only from objects in the shared scope (plus each viewer's own private links to those objects). One teammate's private Notes linked to a shared Task stay invisible to others.
- **Handoff:** the handoff Context Set is filtered to what the recipient will see after accepting. If important context is private to the sender, the engine flags "additional private context exists" **to the sender** (prompting them to share or summarize) and never exposes it to the recipient automatically.
- **Usage signals** are per-user and never surfaced to other users.
- **No side channel:** rankings, counts, and "strongly related" indicators must not reveal the existence or content of an object the viewer cannot see. Privacy correctness is a hard invariant, not a rate (§13).

## 12. MVP Context Engine

Smallest version that supports **E2** (assisted connection), **I1**, **I3**, **T1**. Consistent with P1.2 §7 and P2.1 §9.

### MVP
- **Signals:** explicit user relationships (authoritative); structural (shared home Project, Checkpoint anchoring, Idea→Task lineage, Decision supersede chain, Task state); temporal proximity within a work session; basic content similarity (title/body overlap + shared distinctive terms).
- **Confidence:** the four states; corroboration rule (≥2 categories to surface an inferred link; explicit/strong-structural may stand alone); conservative default to Weak.
- **Discovery:** candidate generation + simple typing (structural verbs directly; `explains`/`caused by` from Decision↔Task temporal patterns; otherwise `related to`); suppression on reject.
- **Assembly:** purpose-scoped Context Sets for Resume, Decision-recall, Handoff; Direct + Recent + High-confidence layers with caps; Potential layer on demand.
- **Ranking:** provenance > purpose-relevant type > recency > status > project relevance; pinned/dismissed honored; deterministic and explainable.
- **HITL:** accept, reject, correct type, manual create/remove, pin, mark irrelevant.
- **Visibility:** per-viewer scoping; both-endpoints-visible rule; handoff recipient filter + sender flag.
- **Lifecycle:** hybrid persistence; handle edit / delete / supersede / state-change / stale.

### Later
- Learned signal weighting from correction and usage history; per-user adaptation.
- Richer semantic similarity; entity disambiguation; topic clustering.
- Indirect context beyond 2 hops; path-explanation UI.
- Detailed confidence explanations; suggestion batching.
- Relationship-type inference beyond the simple patterns.
- Cross-session temporal modelling; usage-graph signals.

### Explicitly out of scope
- External / integration signals (GitHub, chat) — Phase 4.
- Any natural-language output, summarization, recommendation, or next-action generation — P2.3.
- Technology choices: graph store, embedding method, retrieval engine, model/provider, event-vs-batch, storage — §14.
- Team analytics or cross-user aggregate insights.
- Automatic acceptance of inferred relationships without user confirmation.

## 13. Evaluation / Quality Criteria

What to measure eventually (no invented numeric targets):

- **Discovery usefulness** — share of engine-surfaced relationships users accept/keep vs reject.
- **False-positive rate** — surfaced inferred relationships later rejected or dismissed.
- **False-negative signal** — manual links later created between two objects the engine held but did not surface.
- **User correction rate** — type corrections and removals per surfaced relationship; should trend down as context accumulates, not as the user organizes (principle 6).
- **Manual-linking reduction** — manual links per active Task over time; expect decline as engine coverage grows, without loss of graph quality.
- **Context retrieval usefulness** — for a Resume/Recall Set, did the user act from the Set or leave the workspace to reconstruct anyway (pin rate, "explore related" reliance, external tool switches).
- **Reconstruction-effort reduction** — steps/time from opening a stale Task to first productive edit; plus qualitative "did you have what you needed".
- **Handoff completeness** — recipient follow-up questions to the sender per handoff; context items the recipient adds immediately after accepting.
- **Ranking quality** — position within the Set of the item the user first acts on.
- **Set stability** — churn between sessions when nothing relevant changed (should be low).
- **Privacy correctness** — zero incidents of an object appearing in the Context Set of a user who cannot see it (hard invariant).

## 14. Open Technical / Product Decisions

Leave unresolved until architecture/implementation forces them:

- Graph/relationship representation and storage (native graph vs relational vs other).
- Whether embeddings are used at all; if so, technique, generation, storage, provider.
- Entity/topic extraction method and index structure.
- Retrieval/search mechanism for candidate generation.
- Event-driven vs batch vs hybrid inference; latency budget for surfacing suggestions.
- Recalculation frequency and scope (incremental vs periodic full rescore).
- How signal weights are initially set and whether/how they are learned; per-user vs global.
- Where Context Sets are computed (on read vs precomputed/cached) and how they are invalidated.
- Confidence score scale/representation and threshold values.
- Model selection for any ML-assisted step (deferred; must not preempt P2.3's provider work).
- Storage and retention of usage signals.
- Product-level: per-layer item caps; default work-session window length; whether inferred `blocked by` may ever affect Task status without confirmation (current design: **no**).

## Consistency with P2.1

No contradiction found. P2.1 §8 ("Whether the workspace *suggests* relationships automatically is P2.2") and P2.1 §9 (automatic connection inference "out of scope for P2.1 … P2.2") explicitly delegate this design.
