# P2.5 — Architecture Decision

## 1. Decision Status

**Status:** DECIDED (pending user acceptance of this milestone).
**Scope:** architecture decision only — no code, schema, infrastructure, dependencies, services, UI, AI, search, or migrations.
**Supersedes:** the non-binding recommendation in P2.4 §12. That recommendation was re-derived here from the accepted documents rather than ratified; §4.1 records where this decision **departs** from P2.4.

## 2. Decision Summary

**Selected: Alternative A — a relational-core modular monolith with first-class relationship edges, derived-only indexes, an isolated Assistant process, and C-style seams (transactional outbox, retrieval provider, worker isolation) adopted from day one.**

Four decisions carry the weight, each traced to accepted evidence rather than to convention:

1. **Semantic retrieval and embeddings are OUT of the MVP.** P2.2 §12 defines the MVP content signal as *"basic content similarity (title/body overlap + shared distinctive terms)"* and places *"richer semantic similarity"* in **Later**; P2.2 §16 leaves *"whether embeddings are used at all"* open. MVP retrieval is therefore **lexical**. This overturns P2.4's assumption A4 and removes the vector store from the MVP entirely (§4.Q1).
2. **The Assistant runs as a separate process with no data-store credentials** — decided on egress- and credential-isolation grounds, *not* inherited from P2.4 (whose review established that no accepted document mandates process separation). It is the system's **only** external-egress component and the only consumer of untrusted content (§4.Q2).
3. **Visibility is a conjunctive predicate evaluated on one path, before assembly and before ranking.** `filter → assemble → rank`, never `assemble → rank → filter`. Indexes are never authorization (§4.Q3, §15).
4. **Event-driven topology (C) is rejected for the MVP but its seams are adopted.** C's projection lag directly conflicts with R3 ("explicit relationships immediately honored") — C is not merely premature here, it is partially *incorrect* for an accepted requirement (§4.Q7).

Alternative A wins the weighted matrix at **212 / 230** vs B **159** and C **153** — and, critically, **still wins when every simplicity criterion is removed** (§9.3). Simplicity did not decide this.

## 3. Requirements Driving the Decision

The decision turns on these, in descending influence. Every one is an accepted requirement, not an aspiration.

| Driver | Requirement | Why it drives architecture |
|---|---|---|
| **Privacy is a hard invariant, not a rate** | R9, R9a, C3; P2.2 §13 "zero incidents" | The one property with a zero-tolerance target must be structurally enforced, not conventionally. Decides §15 and heavily weights the A/B comparison. |
| **Explicit relationships are authoritative and immediately honored** | R3, C2 | Rules out any topology where the authoritative relationship read passes through an eventually-consistent projection. Directly disqualifies C's core mechanism for MVP. |
| **Reproducible + explainable ranking** | R7, C6 | Every ranking input must be inspectable and versioned; favours all-inputs-are-rows over opaque engine-native scoring. |
| **MVP content signal is lexical** | P2.2 §12 | Removes the vector store, the embedding pipeline, and external egress of object text *for retrieval* from the MVP. Materially simplifies all three alternatives — and dissolves B's and C's retrieval arguments. |
| **Assembly is a bounded-neighborhood operation** | R6 (2-hop cap, per-layer caps); P2.4 §4/A1 as corrected | The workload is not graph analytics. B's headline advantage is dormant under MVP scope. |
| **Assistant is a consumer, never a system of record; output is untrusted; writes need confirmation** | R11, R12, R13, C1, C4 | Decides the Assistant's boundary, credentials, and write surface (§14). |
| **Provenance and authorship are structural** | R8, C5, R15 | Must be schema-level from the first commit and must survive indexing. |
| **Individual-first, team as a thin layer** | R17, C9 | Solo must work with no team infrastructure running; sharing is rows, not a service. |
| **Phase-4 additivity** | R19, C8 | External activity enters as more objects/relationships/signals — not as a second architecture. |
| **Unfiled + mutable captures; activity history; telemetry** | R21, R22, R23 | Shape the physical model (nullable home, mutable type, append-only activity, telemetry that cannot widen R9). |
| **Visible vertical slices; avoid unnecessary complexity** | R20; project operating instructions | A tiebreaker only — deliberately given low weight so it cannot decide the outcome (§5). |

**Conflict resolved:** where the *future aspiration* of rich semantic retrieval meets the *MVP requirement* of a lexical content signal, **the MVP requirement governs**. Consequence: MVP recall will be weaker for paraphrased content; this is accepted, measured via R23, and reversed by adding a retrieval provider (§13.3) — not by re-opening the architecture.

## 4. Resolved P2.4 Questions

### Q1 — MVP retrieval / embeddings / external-AI egress **[RESOLVED]**

| Sub-question | Decision | Evidence |
|---|---|---|
| Is semantic retrieval required in MVP? | **No.** MVP retrieval is lexical: full-text over title/body plus a derived distinctive-term index, combined with structural, temporal and usage signals. | P2.2 §12 MVP ("basic content similarity — title/body overlap + shared distinctive terms"); "richer semantic similarity" is listed under **Later**. |
| Are embeddings required in MVP? | **No.** No embedding pipeline, no vector store, no similarity model in v1. | P2.2 §16 leaves "whether embeddings are used at all" open; nothing in P2.2 §12 MVP requires them. **P2.4's A4 is overturned** — it assumed embeddings were needed and was never checked against P2.2 §12. |
| May object text leave the trust boundary? | **Only through the Assistant, only inside an already visibility-filtered Context Set, and only on explicit user invocation.** No background, batch, or engine-initiated egress. The Context Engine has **no outbound external network path at all**. | R11/R12 (Assistant is a separate consumer); P2.3 §11 (visibility inherited); P2.4 §14 risk row ("keep the Engine with no external egress"). |
| Privacy implications | Egress is reduced to **one component, one direction, one trigger**. Because retrieval is lexical, *no* object text is sent anywhere for indexing — the corpus never leaves. The only content that ever crosses the boundary is what a user's own question caused to be assembled for them. | A7; R9. |
| Architecture consequences | (a) No vector store, no embedding worker, no external index in MVP. (b) The similarity signal is an in-database concern. (c) The egress boundary coincides exactly with the Assistant process boundary, which makes it auditable. (d) A `RetrievalProvider` seam is still mandated so vectors can be added later **without touching domain code** (§13.3). | — |

**Assumption recorded:** lexical similarity plus structural, temporal and usage corroboration is sufficient to satisfy P2.2's "≥2 corroborating categories" surfacing rule at MVP quality. **Falsification test:** R23's false-negative signal (manual links created between objects the engine held but did not surface) and context-relevance metrics. If lexical recall measurably fails, that is the defined trigger to add the vector provider — an *implementation* change behind an existing seam, not an architecture change.

### Q2 — Deployment / tenancy / self-hosting / trust boundary **[RESOLVED]**

- **Initial tenancy:** a **single hosted deployment serving multiple users**, with a **workspace-scoped data model from day one**. Every object, relationship, index row, and telemetry record carries its workspace scope. Physical per-tenant isolation (separate databases/schemas) is **deferred**, but the scope column is not — retrofitting tenancy is the classic irreversible mistake, and adding it now costs nothing.
- **Self-hosting:** **not a v1 requirement.** P2.4's review established that no accepted document mentions self-host, export, portability or data ownership; that was assumption A2 only. **Consequence:** self-host is not designed for, but the core takes **no dependency on a proprietary managed service**, so it remains possible later. Portability is preserved by the canonical-export invariant (§11 INV-9) — kept because it is cheap, not because it is required.
- **Where the Assistant runs:** **a separate process/deployable, holding no data-store credentials**, reachable only through the Engine's Context API.
- **Trust boundary actually required:** the boundary is not "Assistant vs Engine" as an org-chart split; it is **egress + credentials**. The Assistant is (i) the only component that talks to an external model, (ii) the only component that ingests untrusted content (shared teammate text today, ingested GitHub/chat text from Phase 4), and (iii) a component whose output must never authorize a write.
- **Is a separate Assistant service truly justified now? — Yes, but on re-derived grounds.** The blast radius of a compromised or simply *buggy* Assistant is already bounded for **writes** by R13/C4 (proposals are inert until confirmed) — so process separation is **not** justified by write safety. It is justified by **read and egress safety**: in-process, the Assistant module would have ambient access to the datastore connection, and a single coding error could assemble context that bypasses the visibility predicate and post it to an external model — precisely the zero-tolerance failure. Process + credential separation converts that from a convention into an enforced property, satisfying the brief's requirement that unauthorized retrieval be *structurally difficult*. The marginal cost is low because the typed Context API must exist regardless (P2.4 §15). **Decision principle #2 (security correctness) over #7 (operational simplicity) settles it.**
- **Processes in MVP:** three — (1) core application (workspace + context engine + API), (2) background worker (same codebase, different entrypoint: recomputation, candidate generation, index maintenance), (3) assistant service. Two of the three share a codebase; only the Assistant is a distinct trust zone.

### Q5 — A → C evolution risk **[RESOLVED]** → §18. Verdict: **low-to-moderate risk, conditional on nine invariants**; without them it would be high.

## 6. Alternative A Evaluation

*Relational core; objects and relationships as rows; derived lexical indexes in the same store; modular monolith + worker; isolated Assistant process.*

- **K1 Fit (4).** Relationships are first-class edge rows with type, direction, provenance and confidence — a real graph, stored relationally. What A lacks is a graph *engine*, and the MVP forbids the workloads that would need one (2-hop cap, app-side ranking, no learned/graph-native scoring). Genuinely a 4, not a 5: deep traversal and path-explanation would be awkward.
- **K2 Authorization (5).** The conjunctive rule (§15.2) composes into **one** predicate on **one** query path. Both-endpoints-visible is a join condition; relationship-level scope (R9a) is a column predicate; "no side channel" holds because caps, counts and ranks are computed over an already-filtered set. This is the decisive advantage.
- **K3 Consistency (5).** One transactional store: a confirmed relationship is visible to the next read by construction (R3). No projection lag class exists.
- **K4 Provenance/explainability (5).** Every ranking input is a row in the same consistent store; the factor trace is assembled from the same data that produced the ranking. Versioned weights make R7 trivially satisfiable.
- **K5 Reversibility (4).** Edge rows map 1:1 to graph edges; retrieval and model access sit behind seams. Not a 5 because the risk is code-level, not data-level — addressed by the §18 invariants.
- **K6 Traversal (4).** Recursive queries, hop-capped at 2 with per-layer caps: adequate and bounded, not elegant.
- **K7 Retrieval (5).** Lexical full-text and a derived term index live in the same store as the data — no second system, and index rows stay transactionally consistent with the text they describe.
- **K8 Team (5).** Sharing is rows evaluated by the same predicate as everything else; solo runs with zero share rows and no team infrastructure (C9).
- **K9 Integrations (4).** Additive: new object types plus an ingestion worker feeding the suggestion and signal paths. Not a 5 — high-volume external activity will eventually stress a single store.
- **K10 Migration risk (4).** Data exit is clean; code exit depends on discipline (§18).
- **K11 Velocity (5).** One store, transactional writes, no cross-store reconciliation.
- **K12 Local dev (5).** One database and two-or-three processes; a first vertical slice is reachable (R20).
- **K13 Ops (5).** One backup/restore path, one migration path, one place to reason about leakage.
- **K14 Cost (5).** Lowest at any plausible MVP scale.

**Honest weaknesses:** K1 and K6 are where A is merely adequate; a future "explain the path between these two things across several hops" feature is where it would strain first. Accepted consciously; §18 defines the exit.

## 7. Alternative B Evaluation

*Evaluated in its strongest reasonable form, per P2.4's fair-comparison correction: a graph-core **modular monolith** (not a service fan-out) over a graph product with **native** full-text — with the Q1 decision removing the vector requirement entirely, so B's polyglot penalty largely disappears.*

- **K1 Fit (5).** The best conceptual match. Typed directional edges, neighborhood expansion, and path semantics are native rather than emulated.
- **K2 Authorization (2). — the decisive weakness.** The required rule is not merely "filter the results"; it is that *path existence itself* must not leak (R9's no-side-channel), while relationship-level scope (R9a) and both-endpoints visibility apply at **every expansion step**. In a relational join the predicate composes once and can be proven by inspecting one query path. In traversal it must be reapplied per traversal shape, and each new query shape is a new opportunity to omit it. This is not "graph is complex" — it is that **the accepted security model is materially harder to prove correct under traversal**, against a requirement with a zero-incident target.
- **K3 Consistency (4).** Single store is good; if the product lacks native full-text, index lag reappears.
- **K4 Provenance (4).** Edge properties carry provenance well. Slightly lower than A because the ranking inputs increasingly live in query results rather than inspectable rows, and engine-native scoring must be deliberately *avoided* to satisfy C6.
- **K5 Reversibility (2).** Query language and model are product-specific; P2.4 rated exit hardest here, and nothing in the MVP reduces that.
- **K6 Traversal (5).** Native and fast — but **dormant**: the MVP caps at 2 hops.
- **K7 Retrieval (3).** Product-dependent; a strong native full-text implementation makes this a 4, its absence a 2. Unresolvable without naming a product, which this decision declines to do.
- **K8 Team (4).** Same model; the sharing predicate inherits K2's difficulty.
- **K9 Integrations (5).** External activity is simply more nodes and edges.
- **K10 Migration risk (2).** Highest lock-in.
- **K11 Velocity (3).** Fewer fluent developers; more design time spent proving the security model.
- **K12 Local dev (3).** One database, one app — the container count is fine; query-language fluency is the drag.
- **K13 Ops (3).** Less commoditised backup/restore/HA than relational.
- **K14 Cost (3).**

**Do B's conceptual advantages justify its cost for the actual MVP?** No — and specifically because its advantage (K1, K6) applies to capabilities the MVP explicitly forbids (multi-hop beyond 2, graph-native scoring, learned weighting — all P2.2 §12 "Later"), while its weakness (K2) applies to the requirement with the strictest tolerance. B pays lock-in and a harder security proof for capability it may not use. **If the product later needs genuine multi-hop path explanation, the right answer is a derived graph projection behind A's seams (§18), not a graph system of record.**

## 8. Alternative C Evaluation

*Relational SoT + derived graph projection + dedicated search/vector + event bus.*

- **K1 Fit (5).** Each concern gets its ideal representation.
- **K2 Authorization (3).** Authoritative permissions are relational, but the projection and every index must respect visibility too; correctness relies on re-checking against the SoT before emission — recoverable, but it is four surfaces to keep aligned instead of one.
- **K3 Consistency (2). — disqualifying for MVP.** R3 requires explicit relationships to be *immediately honored*. A projection-backed read is eventually consistent by construction; the workaround (read explicit relationships from the SoT, use the projection only for inferred/traversal) reintroduces the relational path *and* keeps the projection — paying twice. C is not merely premature here; on this requirement it is **partially incorrect**.
- **K4 Provenance (3).** Provenance must survive projection and indexing intact — achievable, but now an ongoing correctness obligation rather than a property of the store.
- **K5 Reversibility (4).** Relational SoT keeps data exit clean.
- **K6 Traversal (5).** / **K7 Retrieval (3).** Best-of-breed — but Q1 removed the vector requirement, so much of this advantage now addresses a need the MVP does not have.
- **K8 Team (4).** / **K9 Integrations (5).**
- **K10 Migration risk (4).** **K11 Velocity (2). K12 Local dev (1). K13 Ops (1). K14 Cost (2).**

**Does C solve real MVP requirements?** Only one — clean authoritative/candidate separation (C2) — and A achieves that with separate tables, separate write paths, and independent recompute and retention. Everything else C buys addresses anticipated scale. Per P2.4's corrected A1 analysis, assembly is a bounded-neighborhood query whose cost tracks anchor degree and visible scope, not corpus size, so the scale case is not yet demonstrated. **Introducing distributed, event-driven infrastructure without a demonstrated requirement is explicitly forbidden by this task's principles. Rejected for MVP; its seams are adopted (§18).**

## 10. Selected Architecture

**Alternative A**, specified concretely enough to build against.

```
                    ┌──────────────────────────────────────────────┐
   user request ───▶│  CORE APPLICATION  (one deployable)          │
                    │                                              │
                    │  ┌────────────┐   ┌───────────────────────┐  │
                    │  │ Workspace  │   │ Context Engine        │  │
                    │  │ (objects,  │──▶│  candidates │ assembly│  │
                    │  │  captures, │   │  confidence │ ranking │  │
                    │  │  mutations)│   └───────────┬───────────┘  │
                    │  └─────┬──────┘               │              │
                    │        │      ┌───────────────▼───────────┐  │
                    │        └─────▶│ Authorization (VisibilityPolicy)│
                    │               └───────────────┬───────────┘  │
                    └───────────────────────────────┼──────────────┘
                                                    │  Context API (typed,
                                                    │  principal-bound,
                                                    │  Unavailable≠Empty)
   ┌────────────────────────────────────────────────▼──────────────┐
   │ ASSISTANT SERVICE   — separate process, NO datastore creds     │
   │ reads Context Sets · posts to suggestion queue · sole egress ──┼──▶ external model
   └────────────────────────────────────────────────────────────────┘

   ┌─────────────────────────┐        ┌──────────────────────────────┐
   │ WORKER (same codebase)  │───────▶│ RELATIONAL STORE (SoT)       │
   │ recompute · candidates  │        │ objects · relationships      │
   │ index maintenance       │        │ suggestions · suppressions   │
   │ (never on request path) │        │ usage · activity · audit     │
   └─────────────────────────┘        │ derived: full-text, terms    │
              ▲                       └──────────────────────────────┘
              └────── transactional outbox ◀───── writes
```

**Components**

| Component | Owns | Explicitly does not |
|---|---|---|
| **Workspace module** | Objects, captures, mutations, ownership/authorship, sharing state, handoff | Decide relevance; call external services |
| **Context Engine module** | Candidate discovery, confidence, lifecycle, purpose-scoped assembly, ranking, the Context API | Generate natural language; hold conversation state; reach the internet |
| **Authorization** | The single `VisibilityPolicy`, applied before assembly | Live in the Assistant or in any index |
| **Worker** | Recomputation, candidate generation, index maintenance, outbox drain, telemetry roll-up | Serve interactive requests |
| **Assistant service** | Intent resolution, reasoning over Context Sets, proposals, conversation state, model egress | Hold datastore credentials; write authoritative data; widen scope |
| **Relational store** | The one system of record | Be reachable from the Assistant |

**Technology deliberately not chosen:** relational product, language/framework, frontend, hosting, model provider, authentication provider. The decision requires a *relational* store with transactional integrity and full-text capability, and a *class* of retrieval — nothing narrower. Product selection is delegated to implementation planning.

## 11. Architecture Boundaries — Invariants

Binding. Each is testable; each traces to accepted evidence. Violating one reopens the architecture question.

| ID | Invariant | Trace |
|---|---|---|
| **INV-1** | Domain logic never depends on retrieval implementation. Domain code expresses a `ContextSetRequest` (purpose, target, scope, principal); it never expresses queries, index names, or provider semantics. | C7; §18 |
| **INV-2** | Relationships are first-class domain objects — typed, directional, with author, timestamp, confidence state, provenance and their **own** visibility scope. **No relationship may be expressed as an ad-hoc foreign key on an object.** (`belongs to` is the one singular relationship; it is stored on the object for integrity but **must be exposed through the relationship read model as an edge**, so no consumer special-cases it.) | R2, R8, R9a |
| **INV-3** | Authorization is enforced **before** context is assembled and **before** it is ranked — `filter → assemble → rank`. No API returns objects or relationships without a principal. Deny by default. | R9, C3 |
| **INV-4** | The Assistant cannot bypass application authorization: no datastore credentials, no query path, principal always propagated from the requesting user, never an ambient service identity. | R12, C4, §14 |
| **INV-5** | Provenance survives indexing and retrieval. Any derived representation either carries provenance or is re-joined to it before emission; a Context Set item without provenance is a defect. | R8, C5 |
| **INV-6** | Search and every index are **derived, never authoritative**, and are fully reconstructible from the system of record by a documented rebuild. Index membership is never authorization. | R3, C2, §15.5 |
| **INV-7** | External AI receives only context explicitly permitted for the requesting principal, assembled by the Engine, on explicit user invocation. No background egress. The Context Engine has no outbound external network path. | R9, A7, Q1 |
| **INV-8** | Transactions and mutation authority remain in the core application. Every workspace mutation is user-confirmed and attributed; assistant proposals are inert until confirmed. | R13, C4, R15 |
| **INV-9** | A canonical export — objects, relationships, provenance, activity, audit, in an open format — must remain producible from the system of record at any time. | Reversibility; A2 (retained as cheap insurance, not a requirement) |
| **INV-10** | Ranking is reproducible: versioned weight sets, a per-item factor trace in every Context Set, no hidden state. | R7, C6 |
| **INV-11** | A future derived graph projection, external search, or vector store can be introduced **without changing domain semantics** — enabled by INV-1, INV-2, INV-6 and the outbox (§18). | Q5 |
| **INV-12** | Solo operation requires no team infrastructure: zero share rows is a fully functional system. | R17, C9 |

## 12. Core Data / Relationship Model Implications

Conceptual model implications, not a schema. No migrations, no DDL.

### 12.1 Objects
- One object identity space with a **mutable type** and a **nullable home scope** (Inbox) — R21. Type-varying attributes live in a flexible per-object structure so re-typing is a field update, not a cross-table move.
- Every object carries: workspace scope, creator, contributors, owner (Task/Project), timestamps, and its home Project (nullable).
- **Work Context is never stored** — it is assembled per request (R1, and Q6's assemble-on-read decision).

### 12.2 Relationships
- Edge records: `from`, `to`, `verb` (the 10-verb vocabulary), `origin` (explicit | structural | inferred), `confidence_state`, `author`, `created_at`, **`visibility_scope`**, provenance.
- **Provenance is typed, not a free-form blob** — any field that drives ranking or explanation must be queryable (C6; P2.4 §11 hidden-coupling (iii)).
- Inverse relationships are derived for display, never stored twice.
- `belongs to` is singular; all other verbs are many-to-many (R2).

### 12.3 Authoritative vs candidate separation (C2)
Three distinct record families with **different write paths and different lifecycles**:
1. **Authoritative** — explicit and user-confirmed relationships. Written only by the confirmed-write path. Never modified by recomputation.
2. **Candidates** — inferred suggestions. Written only by the worker. Freely recomputed, expired, and discarded.
3. **Suppressions and usage signals** — persisted user decisions that are **always reapplied** after any recomputation (R4).

Recomputing candidates must be able to discard and rebuild family 2 entirely **without touching families 1 or 3**. This is the operational test for C2.

### 12.4 Transaction boundaries (P2.4 Q16)
- **Atomic (one transaction):** the object + its `belongs to` + its activity record + the audit entry + the outbox event for a single user action.
- **Asynchronous (via outbox, never in the request transaction):** candidate generation, index maintenance, telemetry roll-up, notification.
- **Explicitly forbidden:** any read path that assumes read-your-write on *derived* data. Authoritative reads are strongly consistent; derived reads are not, and API consumers must be able to tell which they are receiving. Declaring this now is what keeps §18 cheap.

### 12.5 Activity and audit
- Append-only per-object activity (R22) — checkpoints and edits; supports the MVP flat activity list, and a timeline later without remodelling.
- Audit (R15) in a separate append-only schema: actor, time, action, originating conversation, supporting context references.
- Deleting an object removes its relationships while history retains their prior existence (R22, P2.2 §5).

## 13. Retrieval / Search Architecture

### 13.1 MVP signals (all in the system of record)
| Signal | Mechanism | Source |
|---|---|---|
| Explicit relationships | Direct edge reads — authoritative, never inferred | R3 |
| Structural | Shared home Project, Checkpoint anchoring, Idea→Task lineage, supersede chain, owner, Task state | R5 |
| Temporal | Bounded work-session window (value open — P2.4 Q12) | R5, A5 |
| Content | **Lexical: full-text over title/body + a derived distinctive-term index** | P2.2 §12, Q1 |
| Usage | Per-user pins, dismissals, repeat opens | R5 |

### 13.2 Assembly and ranking
Purpose-scoped (Resume / Decision-recall / Handoff): authorization filter → candidate union across signals → dedupe to strongest path → layer (Direct, Recent, High-confidence; Indirect/Historical/Potential on demand) → per-layer caps → app-side ranker with versioned weights emitting a factor trace. Traversal is **capped at 2 hops in the domain contract**, not merely in the query — so a future engine inherits the same bound (R6, R7, INV-10).

### 13.3 The retrieval seam and the trigger to extend it
All content-signal access goes through a `RetrievalProvider` abstraction (INV-1). MVP has exactly one implementation: in-store lexical. **Adding vector retrieval later is an implementation behind this seam — a new provider, no domain change, no architecture change.**

**Defined trigger:** R23's false-negative signal (manual links repeatedly created between objects the engine held but did not surface) or context-relevance metrics falling below the product's bar. Until that evidence exists, embeddings stay out (Q1).

## 14. AI / Assistant Architecture

- **Boundary.** Separate process; **no datastore credentials**; its entire read surface is the Context API and its entire write surface is the suggestion queue (INV-4, R12).
- **Context API contract.** `getContextSet(principal, purpose, target, scope)` returning ranked items with type, metadata, relationships, confidence state, provenance, weight-set version and factor trace. **Typed errors distinguish `Empty` from `Unavailable`** — on `Unavailable` the Assistant reports retrieval failure and offers retry, and must not substitute model priors or conversation history (R16). One additional Set request per turn is permitted; no unbounded looping (P2.3 §6).
- **Egress.** The Assistant is the sole external-egress point (INV-7). Only already-filtered Context Set content for the requesting principal, only on explicit invocation. A redaction/consent point sits at this boundary; its user-facing form is deferred.
- **Untrusted input and output.** Workspace content reaching the model (a teammate's shared Note today; ingested GitHub/chat text at Phase 4) is data, never instruction; model output is a proposal, never a command. Proposals are inert until user confirmation (R13, C4). No tool grants the model a write.
- **Conversation state.** Separate schema owned by the Assistant; never a source of workspace context; promoted only by a confirmed action (R14).
- **Provider.** Behind an `LLMProvider` interface; no provider or model selected (C7).
- **Engine independence.** The core system is fully functional with the Assistant absent — enforceable because the Assistant is a separate deployable (R11).

## 15. Authorization / Visibility Model

The authoritative security model. Designed so that unauthorized retrieval is **structurally difficult**, not prompt-dependent.

### 15.1 Principals and scope
Every context operation carries an authenticated **principal**. There is no system/service identity that can return context to a user. All data is **workspace-scoped**; cross-workspace access does not exist.

### 15.2 The visibility predicate

```
visible(object, u)  ⟺  workspace(object) = workspace(u)
                       ∧ ( owner(object) = u
                           ∨ home_project(object) is shared-with u )

visible(rel, u)     ⟺  visible(from(rel), u)          -- endpoint
                       ∧ visible(to(rel),   u)          -- endpoint
                       ∧ ( scope(rel) = shared          -- relationship-level (R9a)
                           ∨ author(rel) = u )
```

Conjunctive and deny-by-default. An Inbox object (no home Project) is owner-only. The relationship clause is what prevents one teammate's **private link between two shared objects** from leaking to everyone who can see both endpoints — the defect P2.4's review identified (R9a).

### 15.3 Enforcement ordering
**`filter → assemble → rank`.** Candidate generation operates on an already-filtered set; caps, counts, ranks, "N more" indicators and completeness checks are computed **only** over filtered data. Filtering after ranking is forbidden: it leaks the existence of invisible objects through position and count (R9's no-side-channel rule).

### 15.4 Structural enforcement
- **One policy object.** A single `VisibilityPolicy` is the only place the predicate is expressed; every engine query composes it.
- **No unprincipled API.** Repository and engine read operations require a principal — there is no overload that omits one. Absence of a principal is a compile-or-startup failure, not a runtime check.
- **Deny by default.** Unlabelled or unknown scope is invisible.
- **Release gate.** Property-based tests over generated share graphs assert that no object or relationship appears in a principal's Context Set unless the predicate admits it, and that caps/counts are invariant to the existence of invisible data. Privacy correctness is a **zero-incident invariant**, not a metric (P2.2 §13).

### 15.5 Derived representations
Indexes (full-text, distinctive-term, and any future vector or projection) are **derived and never authoritative** (INV-6). Two rules: (a) index hits are candidates, and the authoritative predicate is applied to them before anything is emitted; (b) index membership never implies permission. Partitioning an index by scope is permitted as an optimization but never replaces the authoritative check.

### 15.6 Assistant and search access
The Assistant receives only what the Context API emits for its propagated principal; it cannot request another principal's set or widen scope (INV-4). Search is not a separate authorization surface — it is a signal inside assembly, subject to the same predicate at the same point.

### 15.7 Handoff
The recipient-filtered Context Set is evaluated under the **recipient's prospective post-acceptance scope**. Because it is an intersection of the sender's own visible context with the recipient's, it can expose nothing new about the recipient. Sender-private residue is reported to the sender **only** as an "additional private context exists" flag — never its content, and never to the recipient (R10, P2.2 §11).

### 15.8 Telemetry
Telemetry records identifiers, states and outcomes — **never object content** — and is workspace-scoped, so evaluation (R23) cannot become a privacy side channel.

## 16. Deployment / Tenancy Model

- **MVP:** one hosted deployment, multi-user, **workspace-scoped data model from day one**. Three processes: core application, worker, assistant service. One logical relational database.
- **Tenancy:** logical isolation by workspace scope. Physical per-tenant isolation deferred; the scope column is not, because retrofitting tenancy is irreversible.
- **Self-hosting:** not a v1 requirement (no accepted document requires it). No core dependency on a proprietary managed service, so it remains achievable later.
- **Trust zones:** two — the core zone (application, worker, database; **no outbound external network path**) and the assistant zone (no datastore credentials; the only external egress). Enforced by credentials and network policy, not by convention.
- **Environments:** local development must run the whole system on one machine with one database and seeded deterministic data (R20). Hosting platform, orchestration and CI are implementation choices, deliberately unmade here.

## 18. A → C Evolution Strategy

**Verdict on Q5:** choosing A creates a **realistic migration trap only if the couplings below are left unaddressed**. The data is not the risk — edge rows map 1:1 to graph edges and the relational SoT is exactly C's SoT. **The risk is entirely code-level**, and it is cheap to neutralise now and expensive later.

| Coupling | The trap | Neutralised by |
|---|---|---|
| **Domain model** | Domain code shaped around query mechanics | INV-1: domain expresses `ContextSetRequest` intent |
| **Relationship representation** | Relationships drifting into ad-hoc foreign keys — the single most damaging trap, because it destroys the 1:1 edge mapping | INV-2: all relationships in the relationship model; `belongs to` exposed as an edge |
| **Query patterns** | Unbounded traversal that a future engine must replicate | 2-hop cap in the **domain contract** (§13.2) |
| **Retrieval abstraction** | Provider semantics leaking into domain logic | INV-1 + `RetrievalProvider` (§13.3) |
| **Change propagation** | No event stream → every write must be reworked to feed a projection | **Transactional outbox from day one** — the single highest-value reversibility investment |
| **Indexing** | Indexes becoming authoritative or unrebuildable | INV-6: derived, rebuildable, documented rebuild |
| **Authorization** | The predicate expressed only as storage-specific query fragments | `VisibilityPolicy` expressible both as a composed query predicate **and** as a post-filter (§15.4) |
| **Transaction boundaries** | "Everything is atomic" assumptions that break under eventual consistency | §12.4: small atomic core; forbidden read-your-write on derived data |
| **Code-level assumptions** | Callers unable to tell authoritative reads from derived ones | API distinguishes them explicitly (§12.4) |

**Residual risk: low-to-moderate.** With these invariants, evolving toward C is *additive* — stand up a projection or index as a new outbox consumer, move a `RetrievalProvider` implementation, split a module along the Context API — rather than a rewrite. **Without them it would be high**, which is precisely why they are binding rather than advisory.

**Explicitly not doing now:** no event bus, no projection, no second datastore, no service fan-out. The seams are the deliverable; the topology is not.

## 19. Rejected Alternatives

| Rejected | Reason (traced) |
|---|---|
| **B — graph-core SoT** | Its advantages (native traversal, path semantics) apply to capabilities the MVP caps or defers (2-hop limit, no graph-native scoring, no learned weighting — P2.2 §12); its weakness applies to the zero-tolerance requirement: the no-side-channel + relationship-scope rule must be reapplied at every traversal step, making the accepted security model materially harder to prove (§7 K2). Plus the hardest exit (K5, K10). **Not rejected for complexity.** |
| **C — event-driven hybrid** | Projection lag conflicts with R3's "immediately honored"; solves anticipated scale rather than an MVP requirement; its one genuine MVP contribution (C2 separation) is achieved in A by separate tables and write paths (§8, §12.3). Seams adopted, topology rejected. |
| **Document / KV core** | Its real advantage — trivial re-typing (R21) — is obtained in A by a flexible per-object attribute structure. It cannot express the conjunctive visibility predicate as one composable, provable filter (R9/R9a), which is the decisive criterion. |
| **Local-first / CRDT core** | Team sharing (R10), per-viewer server-side context computation, no-side-channel enforcement (R9) and audit (R15) all require an authoritative server. Viable later as an optional sync layer on top; never as the core. |
| **RAG-only / LLM-as-context-store** | Violates C1, C2, R3, R11, R12: the Assistant would become the system of record, ranking would be neither reproducible nor explainable (R7/C6), and privacy could not be centrally enforced (C3). |
| **Full microservices at MVP** | No requirement calls for independent scaling of Workspace, Engine, Identity or Ranking at present scale; multiplies the privacy and consistency surface against the security priority. The one boundary with a real justification — the Assistant's egress/credential zone — **is** taken (§4.Q2). |
| **Assistant in-process** | Rejected: it would give the Assistant ambient datastore access, so a single coding error could assemble unfiltered context and send it to an external model — the zero-tolerance failure. Write safety alone would have permitted it (R13/C4); read and egress safety do not (§4.Q2). |

## 21. Architecture Decision Records / Consequences

| ADR | Decision | Consequence (accepted) |
|---|---|---|
| **ADR-1** | Relational store as the single system of record | Deep graph analytics are not native; bounded by the 2-hop MVP contract; revisit only via a derived projection (§18) |
| **ADR-2** | Relationships are first-class edge records, never foreign keys | Slightly more query work for simple parent/child reads; in exchange, graph semantics and the §18 exit are preserved |
| **ADR-3** | **No embeddings / vector store in MVP; lexical retrieval only** | Weaker recall on paraphrased content; accepted, measured, reversible behind the retrieval seam |
| **ADR-4** | Assistant runs as a separate process with no datastore credentials | One extra deployable and an inter-process contract; in exchange, egress and credential isolation become structural |
| **ADR-5** | Conjunctive visibility predicate, single policy object, `filter → assemble → rank` | Some assembly optimizations are unavailable (cannot rank globally then trim); privacy correctness becomes provable |
| **ADR-6** | Authoritative / candidate / suppression separation by table and write path | Recompute can rebuild candidates wholesale; slightly more model surface |
| **ADR-7** | Transactional outbox and worker isolation from day one | Small upfront cost; removes the principal A→C migration trap and keeps the interactive path clean |
| **ADR-8** | Assemble-on-read; no Context Set cache in MVP | Latency depends on query efficiency; avoids a staleness class conflicting with R3/R18 |
| **ADR-9** | Workspace-scoped data model; physical tenancy deferred | Slightly wider keys everywhere; avoids an irreversible retrofit |
| **ADR-10** | Indexes derived and never authoritative | Rebuild tooling must exist; index membership can never become an accidental permission |
| **ADR-11** | Versioned ranking weights + factor trace in every Context Set | Slightly larger payloads; satisfies R7/C6 and makes HITL corrections meaningful |
| **ADR-12** | No specific database, language, framework, hosting or model provider selected | Implementation planning must choose them against these invariants, not the reverse |

## 23. P2.6 Implementation Implications

*Implications only — not a plan, not a task list, and not authorization to begin.*

- **Bounded contexts to establish:** Workspace, Context Engine, Authorization, Assistant. The Context API between Engine and Assistant is the contract to define first, because every other boundary depends on it.
- **Invariants become test gates, not documentation:** §11's twelve invariants should be enforceable — architecture/dependency tests for INV-1/2/4/6, property-based privacy tests for INV-3, golden-file ranking tests for INV-10.
- **First vertical slice shape:** the smallest slice that exercises the whole architecture is *capture → auto `belongs to` → assemble a Task's Work Context → display it* — it touches objects, relationships, authorization, assembly and ranking without needing the Assistant, and it demonstrates the product's core promise visibly (R20).
- **Order forced by the architecture:** authorization and the relationship model precede assembly; assembly precedes ranking; all of it precedes the Assistant, which is a pure consumer (R11).
- **What must exist from the first commit and is expensive to add later:** provenance and authorship fields, workspace scope, relationship visibility scope, the outbox, and the principal-bound read API.
- **What must not be built yet:** anything in §17.
