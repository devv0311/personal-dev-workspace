# P2.1 — Personal Developer Workspace

Product/system design document. Defines *what the core workspace is* and *how a developer uses it*. No technology, database, API, backend, auth, AI, or integration design. Context Engine = P2.2; AI Assistant = P2.3; this document is concrete enough for both to build on it directly.

Context: `Claude_Project_Blueprint.md`, `docs/phase-1/P1.1-problem-definition.md`, `docs/phase-1/P1.2-individual-small-team-scope.md`.

Anchors: central problem = *developers repeatedly reconstruct connected context that was never externalized*. Priority = I1 resume interrupted work (individual, primary) and T1 developer handoff (team, primary), on enablers E1 capture / E2 connection / E3 sharing, plus I3 decision recall (secondary). Individual-first.

---

## 1. Workspace Purpose

The workspace is the single place where a developer **externalizes working context as they work** and **re-enters that context later at near-zero cost** — for themselves after a time gap (I1) or for a teammate after a handoff (T1).

It is responsible for:
- Holding the developer's projects, tasks, notes, ideas, decisions, and resources as **linked** objects, not siloed lists.
- Recording **why** work happened (decisions, rationale) alongside **what** happened.
- Maintaining, per unit of work, an always-current **Work Context** view that answers "where am I, why, what's next" without manual reassembly.
- Making a unit of work, with its Work Context, **transferable** to another developer.

It is explicitly **not** responsible for: planning/scheduling work, tracking team throughput, communication, or replacing the issue tracker, editor, or chat tool. It is the connective layer between them (P1.1 §6).

## 2. Core Workspace Model

Conceptual model only — no schema.

**Objects**

| Object | What it is | Primary role |
|---|---|---|
| **Project** | A named scope for a body of related work | Home container; the main unit of sharing |
| **Task** | An actionable unit of work with a status | The main unit of *resuming* (I1) and *handoff* (T1) |
| **Note** | Free-form captured text | Default landing place for any quick capture (E1) |
| **Idea** | A candidate for future work, not committed | Kept separate from Tasks so the backlog of "maybe" doesn't pollute active work; can be promoted to a Task |
| **Decision** | A recorded choice: what was chosen, why, alternatives considered, resulting context | The unit of *decision recall* (I3) |
| **Resource** | An external reference (link + why it matters) | Attaches supporting material to work without it living elsewhere |
| **Checkpoint** | A timestamped snapshot on a Task or Project: current focus, progress summary, blockers, next action, open questions | The captured raw material for Work Context; written in-flow (E1) |

**Derived view (not an object the user creates)**

- **Work Context** — the assembled, always-current answer to "where am I on this, why, what's next" for a Task or Project. Composed from: the latest Checkpoint + the object's linked Decisions/Notes/Resources/Ideas + related Tasks + recent activity on the object. This is what I1 and T1 consume.

**Relationships** — first-class, typed, directional links between any two objects. Product semantics in §8. Relationships are the mechanism by which "connected context" stops being mental and becomes part of the workspace.

**Ownership/authorship** — every object records its creator and any later contributors, and a current owner for Tasks/Projects. Authorship is never rewritten by sharing or handoff (§4).

## 3. Individual Developer Experience

The core loop, at product-behavior level.

### Starting / resuming work (I1 — primary)
- The **Home / Resume view** is the default entry point. It lists the developer's in-progress Tasks across all Projects, each showing its latest Checkpoint's *next action* and any *blockers*, most-recently-active first.
- Selecting a Task opens its **Work Context**: latest Checkpoint (focus, progress, blockers, next action, open questions), linked Decisions ("why"), linked Notes/Resources, related Tasks, and recent activity — on one screen, no navigation required to answer "where was I".
- Resuming requires **zero reconstruction**: the developer reads the Work Context and continues. If it is stale, they update the Checkpoint in place (§7).

### Seeing current work context
- Any Task or Project always has a Work Context view. It is assembled by the workspace, not maintained by hand; the only thing the developer maintains is the latest Checkpoint and the links.

### Capturing something while working (E1)
- A **quick-capture** action is available from anywhere in the workspace. The developer types text, optionally picks a type (Note/Idea/Task/Decision/Resource/Checkpoint); if they don't, it lands as a **Note**.
- The capture is automatically attached to the **active work item** (the Task or Project currently in focus) via a `belongs to` relationship. If none is active, it lands in an **Inbox** for later filing.
- Capture never blocks on classification, project selection, or linking. Refinement (retype, move, link) happens later without penalty.

### Finding related context (E2)
- From any object, its **relationships are visible and navigable** — the developer sees what this Task is `blocked by`, which Decision `explains` it, which Idea it was `derived from`, etc., and can traverse in one click.
- The developer can **link objects manually** using the relationship vocabulary (§8). Automated/suggested linking is specified in **P2.2** (Context Engine); MVP relies on manual linking plus the always-on `belongs to` from capture.

### Understanding why something happened (I3 — secondary)
- **Decision** objects capture: the choice, the rationale, alternatives considered, what triggered it (`caused by` a Task/Idea/Note), and what it affects (`explains` / `next action for` Tasks or code references held as Resources).
- From a Task, linked Decisions are shown in its Work Context. From a Decision view, the developer sees its cause and its consequences without searching chat or memory.
- Superseding a Decision creates a new Decision linked `supersedes` → old; the old one stays discoverable but is visually de-emphasised in current context.

### Identifying the next action
- Every Checkpoint has an explicit **next action** field. The Home/Resume view surfaces it per Task. This is a *recorded* next action written by the developer at their last checkpoint — **not** a generated recommendation (generation is P2.3).

## 4. Small-Team Experience

Minimum behavior to support T1 and E3. Deliberately thin; not a collaboration product.

### Developer handoff (T1 — primary)
- A developer can **hand off** a Task (or Project) to a teammate. The handoff transfers the Task's **current owner** and delivers, to the recipient, the Task's full **Work Context** plus a short **handoff note** (what's done, what's expected next, known pitfalls).
- The recipient sees the handoff in a **Handoff Inbox**: the incoming item, its assembled Work Context, the handoff note, and who sent it. Accepting it makes them the owner; the Work Context is already populated — no interrogation of the sender required.
- Handoff does not copy or fork the work; it is the same Task with continuous history.

### Sharing relevant context (E3)
- Default visibility is **private to the author**. Sharing is **explicit**, at **Project** granularity for MVP (share a Project → its objects become visible to named teammates). Object-level sharing is deferred (§9, §10).
- Sharing grants **read** visibility of the shared objects and their Work Context/relationships. It does not create a shared editing surface.

### Receiving another developer's context
- Covered by the Handoff Inbox (above) and by opening a shared Project: the recipient gets the same assembled Work Context and navigable relationships the author had. Reconstruction effort is bounded by *reading*, not *rebuilding*.

### Preserving ownership / authorship
- Every object retains its original **creator**; edits by others add **contributor** entries. Handoff changes the **owner** of a Task/Project only. Nothing about sharing or handoff overwrites authorship or rationale attribution on Decisions.

### Understanding decisions made by teammates
- In a shared Project, **Decision** objects are visible with full rationale, alternatives, author, and timestamp, and with their `caused by` / `explains` links. A teammate answers "why did they choose X" self-serve, without asking the author (T2 is the near-term follow-on; MVP just needs teammate Decisions to be visible and complete).

### Explicitly excluded from the team experience
Comment threads everywhere, @-mentions, real-time co-editing, assignment boards, sprint/iteration planning, permission matrices beyond project share, notification infrastructure, activity analytics, presence. (Consistent with P1.2 §8 Rejected.)

## 5. Workspace Information Architecture

From the user's perspective:

```
Home / Resume view ............ in-progress Tasks across all Projects (I1 entry point)
Handoff Inbox ................. incoming handoffs (T1 entry point)
Inbox ........................ captured-but-unfiled objects

Project (primary scope, unit of sharing)
├── Tasks .................... actionable work; each has a Work Context + Checkpoints
├── Decisions ............... choices + rationale for this project (I3)
├── Notes ................... free-form context
├── Ideas .................. uncommitted candidates
├── Resources ............. external references
└── Related work/context ... links to objects in OTHER projects
```

Rules:
- Every object has **exactly one home Project** (or sits in the Inbox until filed). One home keeps navigation predictable.
- An object may be **linked** to objects in other Projects (`related to`, `blocked by`, etc.) without changing its home. These surface under "Related work/context".
- **Task** and **Decision** are the two objects with dedicated detail views, because they carry I1 and I3.
- Navigation depth to answer "where am I / why": **Home → Task** (1 hop) for resuming; **Task → linked Decision** (1 hop) for why.

## 6. Context Visibility

What each view must show, to minimize reconstruction:

**Viewing a Project**
- Purpose/description; owner and contributors.
- In-progress Tasks with their next actions and blockers.
- Recent Decisions (latest first) with one-line rationale.
- Recently captured Notes/Ideas/Resources.
- Links to related work in other Projects.

**Viewing a Task**
- Status, owner, home Project.
- **Work Context**: latest Checkpoint (focus, progress, blockers, next action, open questions).
- Linked Decisions (`explains` / `caused by`), Notes, Resources.
- Related/`blocked by`/`follows from` Tasks.
- Activity: checkpoints and edits over time (list; browsing history is deferrable — §9).

**Resuming work (Home → Task)**
- Everything in the Task view, with the latest Checkpoint's **next action** and **blockers** shown first.
- A clear indicator of **how stale** the latest Checkpoint is (time since written).

**Viewing a Decision**
- The choice; rationale; alternatives considered; author; timestamp.
- `caused by` (triggering Task/Idea/Note); `explains` / `next action for` (affected Tasks/Resources).
- `supersedes` / `superseded by` links if any.

**Receiving a handoff**
- The Task's full Work Context (as above).
- The **handoff note** (done / expected next / pitfalls).
- Sender identity and time; original creator preserved.
- Open questions from the latest Checkpoint, surfaced prominently.

## 7. Capture Model

Prioritizes E1: frictionless, in-flow, attached to current work.

**Capturable types:** Note (default), Idea, Task, Decision, Resource, Checkpoint.

**Minimum context that must accompany every capture (auto-attached, not asked):**
- Timestamp.
- Author.
- Attachment to the **active work item** (`belongs to` the focused Task/Project), or Inbox if none.

**Optional at capture, addable later without penalty:**
- Type (defaults to Note).
- Title.
- Additional relationships (`caused by`, `blocked by`, …).
- Move to a different home Project.

**Behavioral rules:**
- Quick-capture is reachable from every view with one action and accepts plain text immediately.
- No mandatory fields beyond the text itself.
- A **Checkpoint** capture is a structured quick-capture: focus / progress / blockers / next action / open questions, any field skippable. It is the primary in-flow habit that makes I1 and T1 work.
- Misfiled or untyped captures are expected and cheap to fix; the workspace must make refinement a normal, low-friction action, not a correction.

(Technical implementation of capture — clients, hotkeys, editor hooks — is out of scope.)

## 8. Relationship Model

Product semantics. Relationships are typed and directional (A → verb → B). No graph/storage design.

| Relationship | Meaning | Typical use |
|---|---|---|
| `belongs to` | A's home context is B | Task → Project; any capture → active work item |
| `derived from` | A was created out of B | Task `derived from` Idea; Note `derived from` Decision |
| `explains` | A gives the reason for B | Decision `explains` Task; Note `explains` Decision |
| `caused by` | A exists because of B | Decision `caused by` Issue/Idea; Task `caused by` Decision |
| `blocked by` | A cannot progress until B resolves | Task `blocked by` Task; Task `blocked by` open question |
| `next action for` | A is the concrete next step for B | Task `next action for` Decision/Project |
| `follows from` | A comes after B in a sequence | Task `follows from` Task |
| `related to` | A and B share context, unspecified | any ↔ any (default weak link) |
| `references` | A points at B as supporting material | Task `references` Resource |
| `supersedes` | A replaces B | Decision `supersedes` Decision |

Rules:
- `belongs to` is singular (one home). All others are many-to-many.
- Every relationship records who created it and when (so a handoff recipient can trust the graph).
- `related to` is the safe default when the precise verb is unknown; it can be refined later.
- The inverse of each link is shown automatically on the other object (e.g. B shows "explained by A").
- Whether the workspace *suggests* relationships automatically is **P2.2**; P2.1 requires only that users can create and traverse them and that capture auto-creates `belongs to`.

## 9. MVP Boundary

Consistent with P1.2 §7 (MVP = E1, E2, E3, I1, I3, T1).

**Required for the first usable workspace**
- Objects: **Project, Task, Note, Decision, Checkpoint**.
- **Quick-capture** attached to active work item; Inbox for unattached captures; low-friction refinement.
- **Manual typed linking** with the §8 vocabulary; auto `belongs to` on capture; navigable relationships with inverses.
- **Work Context** assembly for Task and Project.
- Views: **Home/Resume**, **Project**, **Task**, **Decision**, **Handoff Inbox**.
- **Checkpoints** on Tasks with next-action and blockers; staleness indicator.
- Single-developer use fully functional without any team feature.
- **Project-level sharing** (explicit, read visibility) and **Task/Project handoff** with Work Context + handoff note.
- **Authorship**: creator + contributors on every object; owner on Task/Project.

**Useful but deferred**
- **Idea** and **Resource** as distinct objects (MVP: an Idea is a Note tagged "idea"; a Resource is a Note with a link). Promote to first-class post-MVP.
- **Object-level** sharing granularity (MVP is Project-level).
- Checkpoint **history browsing / timeline** (MVP shows latest + a flat activity list).
- Cross-project **saved views / dashboards**.
- Relationship types beyond the core set; relationship strength/weighting.
- Handoff **acceptance workflow** niceties (accept/decline/return, handoff history).
- **Idea → Task promotion** preserving `derived from` automatically.

**Out of scope for P2.1 (and MVP)**
- Automatic connection/relationship inference — **P2.2**.
- AI assistant, Q&A, summarization, generated next actions, semantic search — **P2.3**.
- External integrations (GitHub issues/PRs/commits, chat) — Phase 4.
- Generic project management: boards, sprints, estimates, burndown, Gantt, time tracking, capacity.
- Team chat, comment threads, notifications infrastructure, presence, real-time co-editing.
- Technology stack, database, API, backend, auth, and AI architecture.
- Mobile / offline design.

## 10. Open Product Decisions

Genuinely unresolved; must be decided with later design/validation, not now.

1. **Primary context unit** (P1.2 Q6): are Checkpoints best anchored at Task level, Project level, or a separate "work session" spanning multiple Tasks? Current design assumes Task-level with optional Project-level; unvalidated.
2. **Work Context assembly**: fully auto-assembled vs. developer-curated. Auto reduces E1 friction but may surface noise in I1/T1; curation improves signal but adds work. Likely a default + override, exact balance open.
3. **Capture classification timing** (P1.2 Q1–Q2): infer/refine type later (chosen default) vs. prompt at capture. Affects friction vs. immediate structure.
4. **Sharing granularity** (P1.2 Q4): is Project-level sharing sufficient for credible handoffs, or is object-level sharing required in MVP?
5. **Handoff semantics**: transfer ownership (current design) vs. share + assign vs. clone context. Also: is an accept/decline step needed for MVP?
6. **External context in handoff** (P1.2 Q5): does T1 deliver validated value with manually captured context only, or is GitHub/issue context required to be credible?
7. **Solo → team transition** (P1.2 Q7): what event turns a solo developer's private workspace into shared team context without a migration step?
8. **Decision lifecycle**: how superseded Decisions stay discoverable (search, project archive, link-only) without cluttering current Work Context.
9. **Idea lifecycle**: on promoting an Idea to a Task, what history/links persist, and does the Idea remain or convert.
10. **Staleness handling**: does the workspace only *indicate* Checkpoint staleness (current design), or also prompt/nudge for a fresh Checkpoint — and does nudging belong in product behavior or in P2.3.
