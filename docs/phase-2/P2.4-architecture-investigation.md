# P2.4 — Technical Architecture Investigation

**This is an investigation, not a decision.** It surfaces and compares viable architecture approaches for the product defined by the Blueprint and the accepted P1.1–P2.3 documents. It does **not** select the final architecture (that is P2.5) and prescribes no technology except where the analysis shows a class of technology is required by a stated requirement.

Inputs read: `Claude_Project_Blueprint.md`, `docs/PROGRESS.md`, `docs/phase-1/P1.1`, `docs/phase-1/P1.2`, `docs/phase-2/P2.1`, `docs/phase-2/P2.2`, `docs/phase-2/P2.3`. Repository state: documentation-only; no application code, no build config, no CI; git with `main` (stable) and `develop`.

---

## 1. Objective

Determine which architecture *shape* best fits the actual, documented requirements of the Personal Developer Workspace, its Context Engine, and its AI Assistant — evaluating at least three independent approaches across every dimension listed in the P2.4 brief — and identify the strongest candidate plus the decisions P2.5 must still make. Every recommendation traces to a numbered requirement (Rn) or constraint (Cn) below.

## 3. Architectural Constraints

Non-negotiable shape constraints (stronger than requirements — they rule options in or out).

| # | Constraint |
|---|---|
| C1 | **Component boundary:** Context Engine and AI Assistant are distinct deployable/process units with a one-way dependency (Assistant → Engine). The Engine runs standalone. |
| C2 | **Store separation:** the authoritative relationship store and the inferred/candidate store have different lifecycles and MUST be separable (independent recompute, suppression, and retention of the candidate side without touching authoritative rows). |
| C3 | **Privacy enforced in the Engine, centrally:** visibility filtering happens before any context leaves the Context Engine; permission logic is not in the Assistant; it should be enforced at as few code paths as possible to be auditable. |
| C4 | **Confirmed-write-only path:** all mutations flow through one explicit user-confirmed path; assistant/model output cannot trigger a write, a permission change, or an engine-config change on its own. |
| C5 | **Provenance/authorship are structural**, present on every relationship and object from the first schema — not a later addition. |
| C6 | **Reproducible + explainable ranking:** given identical inputs the ranked Context Set is identical, and the engine can state which factors placed each item. Ranking weights must therefore be explicit and versioned. |
| C7 | **No prescribed technology from prior docs:** the open-decision lists in P2.2 §16 and P2.3 §16 (graph representation, embeddings, retrieval mechanism, event-vs-batch inference, recalculation frequency, model selection, storage, conversation persistence) remain open here. |
| C8 | **Phase-4 additivity:** external activity is ingested as more objects/relationships/signals into the same model; the core must not assume the workspace is the only data source. |
| C9 | **Solo has no hard multi-tenant dependency:** single-user operation must not require a running sharing/permission service or team infrastructure. |

## 6. Context Engine — architectural implications (called out per the P2.4 brief)

The architecture must preserve, regardless of alternative:

- **Explicit relationships** — a first-class, authoritative, immediately-consistent store, physically/logically separate from inferred candidates (R3, C2). *Implication:* the SoT for relationships cannot be a lossy projection or a similarity index; it is a transactional record.
- **Purpose-scoped Context Sets** — assembly is a parametrised operation over the relationship + object stores plus the signal indexes, producing a bounded, ranked, layered result (R6). *Implication:* the engine needs cheap structural traversal to ~2 hops, a similarity lookup, a temporal filter, and an app-controlled ranker; it does **not** need arbitrary-depth graph analytics in the MVP (P2.2 §12).
- **Provenance** — carried on every edge/object row and returned in the Context Set (R8, C5). *Implication:* schema-level, not a log-only afterthought.
- **Privacy boundaries** — one enforcement point inside the engine, applied before emission; both-endpoints-visible for cross-Project links; no counts/rankings computed over rows the viewer can't see (R9, C3). *Implication:* prefer an architecture where the visibility predicate lives in **one** query path.
- **User authority + confirm-before-write** — inferred links never auto-promote; writes are one confirmed path (R13, C4). *Implication:* the candidate store is append/adjust-only from the engine; promotion to authoritative is a user-triggered transaction.
- **Assistant-as-untrusted output** — the engine exposes a read API returning structured, already-filtered context; it accepts *suggestions* from the Assistant only through the same HITL queue a human suggestion uses (R12). *Implication:* the engine's write surface for the Assistant is exactly the suggestion queue, nothing more.
- **Graceful context-retrieval failure** — the engine API distinguishes "empty result" from "unavailable"; the Assistant gateway maps unavailability to a retry-offer, never a fallback (R16). *Implication:* a typed error contract on the engine API.

These do not by themselves pick an alternative, but they penalise any option that spreads the visibility predicate across many code paths (EC2) or blurs the authoritative/candidate boundary (EC3).

## 7. Architecture Alternative A — Relational-core modular monolith with pluggable retrieval

**Shape.** One deployable application ("workspace + engine") with enforced internal module boundaries (Workspace, Context Engine, Identity/Sharing), plus a **separate** Assistant service (the untrusted boundary, C1/R11). A single relational database is the system of record. Content search and vector similarity are provided by the relational engine's own capabilities or first-class extensions, behind a `RetrievalProvider` interface so they can move out later.

| Dimension | Analysis |
|---|---|
| Application architecture | Modular monolith; Context Engine exposed via an in-process API with the *same* contract it would have as a service (typed errors per R16). Assistant is out-of-process from day one — it must be, to keep C4/R12 honest. |
| Data / storage | One relational DB. Objects: a shared `object` table (id, type, owner, created_by, timestamps, home_project) + per-type detail tables; `contributor` table. Relationships: one `relationship` table (`from`, `to`, `verb`, `origin ∈ {explicit,structural,inferred}`, `confidence_state`, `author`, `created_at`, `signals` JSON). Candidate churn isolated in `relationship_suggestion` and `relationship_suppression` tables → C2 satisfied without a second datastore. `usage_signal` table (per-user). `audit_log` table (R15). |
| Search / retrieval | Full-text index for the content signal + a distinctive-term/entity index (derived table). Vector similarity via the DB's vector capability/extension — one store, one backup, embedding row transactionally consistent with its object text. Structural traversal (shared Project, `supersedes` chains, Idea→Task lineage, 1–2-hop indirect context) via recursive CTEs, hop-capped per R6. |
| Context / relationship model | Relationships are edge rows. Context Set assembly = a parametrised query plan per purpose (Resume/Decision-recall/Handoff) that unions the signal queries, then an **app-side ranker** applies versioned weights (C6) and emits a factor breakdown (R7). Reproducible because every input is a row. |
| AI integration | Assistant service behind an `LLMProvider` interface (no provider chosen, C7). It calls only `ContextEngine.getContextSet(purpose,target,scope,user)` and posts to the suggestion queue (R12). Engine unavailability → typed error → retry-offer (R16). |
| AuthN / AuthZ | Identity/Sharing module. Authorization = a single visibility predicate composed into every engine query by one query-builder (C3, EC2). `project_share` rows drive it. Both-endpoints-visible enforced in the relationship query's join. Side-channel-safe: counts/rankings are computed only over the already-filtered row set. |
| Individual + small-team | Solo = one owner, zero `project_share` rows, sharing module dormant (C9/R17). Team = insert shares. No new infrastructure. |
| GitHub / integration readiness | Phase-4 = new `object.type` values + an ingestion worker writing objects and feeding `relationship_suggestion` / `usage_signal`. Purely additive (R19/C8). |
| Local dev | One DB container + app + an Assistant stub. Single `docker compose up`; deterministic seed data. Best time-to-first-slice (R20/EC7). |
| Testing | Rankers and scorers are pure functions (unit). Assembly: DB-fixture integration tests. Engine API: contract tests reused when/if extracted. Privacy: property-based tests asserting no object crosses a scope boundary over generated share graphs. Assistant: fake engine + fake LLM. Determinism (R7) makes golden-file ranking tests viable. |
| Deployment / ops | 2 services + 1 DB. One backup/restore path. Standard migrations. |
| Scalability | Vertical + read replicas; tenant partitioning later. Comfortably covers A1; not built for 10⁶-user social scale (not required). |
| Performance | Hot path (assembly) is one DB round trip (CTE + vector + full-text) then in-proc ranking; assembled Sets cacheable with write-triggered invalidation. Meets A3. Weak at deep graph analytics — out of MVP scope. |
| Security / privacy | Single store → one encryption-at-rest config, one audit log, one place to reason about leakage. Row-level scoping is inspectable. Strongest EC2/EC5 story. |
| Data ownership / portability | One logical dump = complete export (EC14 ✓✓). Self-host = 1 DB + 2 services (EC15 strong). |
| Development velocity | Highest: familiar model, transactional writes, no cross-store sync code. |
| Operational complexity | Lowest (EC12 ✓✓). |
| Cost | Lowest (EC13 ✓✓). |
| Major risks | (a) Vector-extension performance ceiling at growth → mitigated by the `RetrievalProvider` seam (swap to a dedicated vector store without schema change). (b) Modular boundary erosion → mitigated by the pre-defined engine API + architecture tests. (c) Recursive-CTE cost if indirect hops grew past 2 → bounded by R6 caps; precompute if needed. (d) Highly-connected object hot rows → indexes + per-layer caps. (e) A1 wrong → extraction path (below). |
| Migration / exit | Engine already has a service-grade API → lift to its own service. Embeddings behind an interface → move to a dedicated vector DB. Explicit-relationship rows map 1:1 to graph edges → a later graph projection is a straight ETL. Canonical relational export bounds lock-in. |

## 8. Architecture Alternative B — Graph-core (native graph database as system of record)

**Shape.** Services around a native graph database that stores objects as nodes and relationships as edges. Context Engine leans on graph pattern-matching and traversal. Full-text and (almost certainly) vector search are **external** indexes, so the system is already polyglot. Assistant service as in A.

| Dimension | Analysis |
|---|---|
| Application architecture | Workspace service + Context Engine service (thin — much logic is graph queries) + Assistant service. |
| Data / storage | Graph DB is SoT. Nodes = objects; edges = relationships with properties (`verb`, `origin`, `confidence_state`, `author`, `ts`, `signals`). Authoritative vs inferred = edge label/property; suppressions = edges or a side store. Provenance = properties. **C2 concern:** authoritative and candidate edges live in the same store and are separated only by convention/labels, not by lifecycle isolation. |
| Search / retrieval | Graph-native full-text varies by product; vector search is external → a separate vector DB from day one. Candidate generation = graph patterns + external similarity lookup then re-hydrate in the graph. Indirect-context traversal is native and cheap. |
| Context / relationship model | Best *conceptual* fit for "typed directional relationships" and multi-hop assembly. But ranking still must be app-side for explainability/reproducibility (R7/C6) — graph-native scores (e.g. centrality) are out of MVP scope and less explainable — so the graph's headline advantage is only partly used. |
| AI integration | Same separate untrusted service + suggestion queue. |
| AuthN / AuthZ | Visibility must be applied inside **every** traversal. Enforcing both-endpoints-visible and no-side-channel across arbitrary traversal shapes is harder to centralise than a single SQL predicate → **weaker EC2**, more surface for a privacy defect. |
| Individual + small-team | Conceptually identical model; fine. |
| GitHub / integration readiness | Excellent — external activity is just more nodes/edges (EC9 ✓✓). |
| Local dev | Graph DB + external search + external vector + app. Heavier local stack; fewer developers fluent in the query language; slower first slice (EC7 weaker). |
| Testing | Traversal queries are harder to fixture and exhaustively assert; privacy property tests must cover many traversal shapes. Ranking still testable. Net EC16 weaker than A. |
| Deployment / ops | Specialised operational knowledge (backup/restore, HA, upgrades less commoditised) **plus** running and reconciling separate search + vector stores with no cross-store transactions → consistency glue code. EC12 poor. |
| Scalability | Graph DBs read-scale well; clustering/write-scaling can be licensed/costly. Exceeds A1 need (EC10 — headroom not required). |
| Performance | Multi-hop traversal is fast, but the MVP caps at ~2 hops (P2.2 §6), so the advantage is largely dormant; cross-store hydration adds latency on the hot path. |
| Security / privacy | Multiple stores → multiple encryption/audit configurations; unified audit log needs aggregation. EC2/EC5 weaker than A. |
| Data ownership / portability | Export spans graph dump + search + vector; self-host runs three systems (EC14/EC15 weaker). |
| Development velocity | Slower initially: fewer fluent developers, more moving parts, consistency code. |
| Operational complexity | High. |
| Cost | Higher (managed graph + vector + search, or heavier self-host ops). |
| Major risks | (a) Query-language / vendor lock-in (Cypher vs GQL vs proprietary). (b) Privacy predicate spread across traversals. (c) Polyglot consistency bugs. (d) Hop-cap makes the core advantage marginal for the MVP. (e) Hiring/knowledge risk. |
| Migration / exit | Hardest: data model and query language are product-specific; moving off graph is a Context Engine rewrite. |

## 9. Architecture Alternative C — Hybrid: relational source-of-truth + derived graph projection + dedicated vector/search indexes (event-driven)

**Shape.** Relational DB is authoritative for objects, explicit relationships, provenance, sharing, and audit. A **derived** graph projection (rebuilt from an event stream) serves traversal and inferred-candidate maintenance. A dedicated vector DB and a dedicated search engine serve semantic and full-text signals. The Context Engine owns the projection + a separate candidate store. Assistant service as in A. Components communicate over an event bus.

| Dimension | Analysis |
|---|---|
| Application architecture | Workspace service (owns relational SoT) + Context Engine service (owns projection, candidate store, index fan-out) + Assistant service + event bus + projection workers. |
| Data / storage | Relational SoT for objects / explicit relationships / provenance / sharing / audit. Inferred candidates + suppressions + usage signals in the engine's **own** store → **cleanest C2**. Graph projection is disposable and rebuildable. Vector DB + search engine are best-of-breed. |
| Search / retrieval | Best-of-breed per concern; candidate generation fans out across search + vector + projection; ranking app-side (R7). |
| Context / relationship model | Strong: SoT integrity from relational, traversal speed from the projection, semantic recall from vectors. But a just-created explicit relationship not yet in the projection would be missed → contradicts R3's "immediately honored" unless explicit relationships are always read from the SoT directly and the projection is used only for inferred/traversal — extra code and a subtle correctness rule. |
| AI integration | Same separate untrusted service + suggestion queue. |
| AuthN / AuthZ | Authoritative permissions in relational, but the projection and both indexes must respect visibility too. Mitigation: the engine resolves final visibility against the relational SoT before emitting any Set (one checkpoint) — restores EC2 at a latency cost and with more moving parts to keep aligned. |
| Individual + small-team | Same model — but running an event bus + projection workers + three datastores to open a solo notes app is disproportionate (EC6/EC18 poor). |
| GitHub / integration readiness | Excellent — new event sources, projection and indexes absorb them (EC9 ✓✓). |
| Local dev | Heaviest stack; the event pipeline must be running before anything appears; slowest onboarding; directly in tension with R20/EC7. |
| Testing | Highest burden: eventual-consistency scenarios, projection-rebuild tests, cross-store privacy tests, event-replay tests. EC16 weakest. |
| Deployment / ops | Highest: bus, workers, 3+ datastores, backfill/rebuild tooling, projection-lag monitoring (interacts with the staleness semantics of R18). EC12 weakest. |
| Scalability | Highest ceiling; each concern scales independently — **far beyond A1**. |
| Performance | Hot path can be fastest once warm, but projection lag adds a consistency/staleness dimension the product must reason about. |
| Security / privacy | Largest attack surface; strongest *possible* isolation but the most configuration to keep aligned; unified audit needs aggregation. |
| Data ownership / portability | Relational SoT gives a clean canonical export (EC14 good); full *system* reproduction is complex (EC15 poor). |
| Development velocity | Slowest to first slice; fastest to add new signal types much later. |
| Operational complexity | Highest. |
| Cost | Highest. |
| Major risks | (a) Premature complexity vs actual scale (A1) — violates "avoid unnecessary complexity" and the "no large invisible infrastructure first" value (R20/EC18). (b) Projection lag vs R3 immediacy. (c) Eventual-consistency defects. (d) Privacy alignment across four stores. (e) Long runway before visible product. |
| Migration / exit | Data export decent (relational SoT); operational/knowledge exit poor. |

## 11. Trade-off Analysis

- **Conceptual fit vs enforceability.** B/C model relationships more "naturally", but the two properties the documents treat as hard invariants — centralised privacy filtering with no side channel (R9/C3) and reproducible, explainable ranking (R7/C6) — are *easier to guarantee and test* when all inputs are rows behind one query path (A). A graph's expressiveness is not the bottleneck; the MVP forbids the features that would exploit it.
- **Scale headroom vs delivery.** C buys independent scaling the product does not yet need (A1) at the cost of the thing the project explicitly values — visible vertical slices and low invisible infrastructure (R20). Headroom that delays the first usable slice is a net negative here.
- **Store separation.** C2 wants authoritative and inferred stores separable. C does this best (distinct store); A does it well enough (distinct tables + distinct write paths + independent recompute/retention); B does it worst (same store, convention-only). A's approach is sufficient for the requirement as written.
- **Portability.** The Blueprint elevates data ownership/portability. A single relational SoT (A, and the SoT half of C) yields a clean canonical export; B's polyglot SoT does not. Self-host — a credible expectation under A2 — is realistic only for A.
- **Extraction path.** A is not a dead end: its pre-defined engine API, `RetrievalProvider`/`LLMProvider` seams, and edge-row model that maps 1:1 to graph edges mean the team can evolve toward B-style traversal or C-style projections **if and when** A1 proves wrong — without a rewrite. The reverse (starting at B/C and simplifying) is far harder.
- **Where C's ideas still apply.** Even under A, three C-flavoured decisions are worth keeping: a *separate* candidate/suggestion store boundary (already in A's design), retrieval behind a provider seam, and a typed event/notification for write→cache-invalidation and future ingestion.

## 12. Recommended Candidate (for P2.5 to ratify or reject)

**Alternative A — relational-core modular monolith with a separate Assistant service and retrieval behind a provider seam — is the strongest candidate**, because it satisfies every hard constraint (C1–C9) and every high-weight criterion at least adequately, with the lowest operational complexity, the best local-dev and portability story, and a non-destructive path to B/C-style components later. B's advantages are dormant under the MVP Context Engine scope; C is over-built for A1 and works against the project's stated delivery values.

This is a recommendation, not a decision. It is contingent on P2.5 confirming A1 (scale), A2 (deployment/self-host), and A4 (embeddings in/out of MVP). If A1 is materially wrong (10⁶+ objects or large teams), re-weight toward C's independently scalable concerns.

## 13. Rejected / Less-preferred Approaches

| Approach | Why not (traced to requirements) |
|---|---|
| **Document / KV / wide-column core** as SoT | Context Set assembly is inherently multi-entity and relationship-centric (R2, R5, R6); ad-hoc join-like assembly and the centralised visibility predicate (R9/C3) are awkward and error-prone without relational joins or graph edges. No compensating advantage at A1 scale. |
| **Local-first / CRDT store as the core** | Attractive for portability (Blueprint §4) and solo use, but team sharing (R10), server-side per-viewer context computation and no-side-channel enforcement (R9), embeddings, and the audit log (R15) all require an authoritative server anyway. Revisit as an *optional sync/offline layer* on top of A, not as the core. |
| **RAG-only / "LLM as the context store"** (no explicit relationship store; retrieve-and-reason over embeddings) | Directly violates C1, C2, R3, R11, R12 — the Assistant would become the de facto system of record for how context connects, ranking would be neither reproducible nor explainable (R7/C6), and privacy could not be centrally enforced (C3). |
| **Full microservices from day one** (separate Workspace, Relationship, Signal, Assembly, Ranking, Identity services) | No requirement calls for independent scaling of these at A1; multiplies operational complexity and cross-service privacy/consistency surface against R20/EC18. The one boundary the documents *do* mandate — Assistant vs Engine (C1) — is honored in A. |

## 14. Risks (cross-cutting, independent of the chosen alternative)

| Risk | Impact | Mitigation |
|---|---|---|
| Embedding/vector performance or cost ceiling | Degrades the content signal (R5) or raises cost | Retrieval behind a provider seam; start with full-text + distinctive-term index, add vectors as a swappable component |
| External-AI egress of sensitive content (A7) | Privacy exposure via the Assistant's LLM calls | Define the Assistant trust zone, egress controls, and a redaction/consent point in P2.5; keep the Engine (which holds all context) with no external egress |
| Privacy filtering defect (side channel via counts/rankings) | Leak of invisible object existence (R9) | Single visibility query path (favoured by A); property-based privacy test suite as a release gate |
| Ranking non-reproducibility (unversioned weights, hidden state) | Violates R7/C6; erodes user trust in HITL corrections | Versioned weight constants (A8); ranker emits a factor trace; golden-file tests |
| "Work session" window undefined (A5) | Temporal signal miscalibrated | P2.5/impl decision; make it configurable |
| Context Set cache staleness vs R3 immediacy / R18 staleness semantics | Stale or missing just-added context | Explicit relationships read from SoT, not cache; write-triggered invalidation; surface "last updated N ago" |
| Scale assumption A1 wrong | Chosen shape under-provisioned | A's extraction path (engine API, provider seams, edge-row model); revisit at defined object-count thresholds |
| Modular boundary erosion (A) | Future extraction becomes costly | Architecture/dependency tests enforcing the engine API boundary |

## 15. Migration / Exit Considerations

- **Keep the Context Engine behind a stable, typed API** (including the error contract for R16) from the first commit, whether or not it is a separate process — this is the single most important reversibility investment.
- **Isolate retrieval** (`RetrievalProvider`) and **model access** (`LLMProvider`) behind interfaces; no provider name in core code (C7).
- **Store explicit relationships as edge rows that map 1:1 to graph edges** so a later graph projection or migration to B is an ETL, not a redesign.
- **Guarantee a canonical export**: a documented, versioned dump of objects + relationships + provenance + audit in an open format — the portability promise (Blueprint §4) and the ultimate exit hatch.
- **Avoid datastore-proprietary features** except the vector capability, which is already behind the seam.
- **Version the ranking weights and the Context Set schema** so behaviour is reproducible across upgrades and a consumer (the Assistant) can detect changes.

## 16. Open Architectural Questions (for P2.5)

1. **Confirm A1 scale.** Target maximum team size and expected workspace object counts / growth curve. Directly decides A vs needing C's independent scaling.
2. **Embeddings in the MVP?** Is the content/semantic signal (R5) delivered with vectors from day one, or with full-text + distinctive-term matching first? If vectors: hosted or self-hosted, and is external egress of object text acceptable (A7)?
3. **Vector search placement.** In-database vector capability vs a dedicated vector store — what performance envelope is acceptable at A1, and what is the trigger to split it out?
4. **Deployment & tenancy.** Single-tenant vs multi-tenant; is self-host a v1 requirement? (Shapes A2 and weights EC15.)
5. **Visibility enforcement pattern.** Mandate a single query-builder / single predicate path? Where is the "both endpoints visible" check implemented, and how is it tested as a release gate?
6. **Context Set assembly mode.** Assemble-on-read vs precompute/cache; invalidation triggers; maximum acceptable staleness (interacts with R18).
7. **Inference scheduling.** Event-driven on capture/edit vs periodic batch vs hybrid (P2.2 §16); latency budget for a suggestion to appear.
8. **Ranking weights.** Where do the versioned constants live, how are they changed, and how is a change surfaced to the Assistant (C6)?
9. **Audit log placement & retention.** Same database as the SoT vs separate; retention period; export inclusion.
10. **Assistant trust zone.** Same network/security zone as the Engine or isolated; egress policy for external LLM calls given A7; where redaction/consent happens.
11. **Conversation store.** Where conversation state lives (not the workspace SoT, R14) — separate schema, separate store, retention, cross-device sync.
12. **"Work session" window.** Definition and default value for the temporal signal (A5).
