# P2.3 — AI Assistant

Product/system design. Defines the AI Assistant that operates **on top of** the Context Engine (P2.2). Not an implementation. No AI provider, model, model-routing, production API, auth, integration, tool-calling, or UI design.

Context (authoritative): `Claude_Project_Blueprint.md`, `docs/phase-1/P1.1-problem-definition.md`, `docs/phase-1/P1.2-individual-small-team-scope.md`, `docs/phase-2/P2.1-personal-developer-workspace.md`, `docs/phase-2/P2.2-context-engine.md`.

Architectural rule inherited from P2.2 §9: the Context Engine discovers relationships, maintains structure, assembles bounded visibility-safe **Context Sets**, and ranks them; the AI Assistant **reasons over those Sets** to answer, summarize, explain, and propose actions. **The assistant is never the system of record for context or relationships.** No contradiction with prior milestones was found (see §"Consistency with prior milestones").

---

## 1. Assistant Purpose

**Problems it solves.** Even with an assembled Context Set, the developer still has to *read and synthesise* it; some questions ("why", "what's missing", "what next") require reasoning across several objects; and turning intent into workspace navigation is itself friction. The assistant converts a natural-language question into a grounded answer built from the engine's Context Set, and converts loose notes/intent into *proposed* structured objects — removing the read/synthesise step of reconstruction.

**Role in Capture → Connect → Understand → Act:**
- **Understand** — primary: answer / explain / summarise over assembled context.
- **Act** — propose Tasks, links, updates, handoffs for user confirmation.
- **Capture** — only indirectly: propose structure from existing captures.
- **Connect** — *not the assistant's job*; that is the Context Engine. Any connection the assistant notices is emitted as a suggestion through the engine's HITL path (P2.2 §8–9), never written directly.

**Makes easier:** resuming (one question vs scanning), decision recall (prose "why" with citations), handoff prep (drafted package + gap list), notes → proposed tasks.

**Explicitly does NOT:**
- Store context or relationships; be a source of truth.
- Run relationship discovery, confidence scoring, ranking, or visibility filtering itself.
- Mutate the workspace without explicit user confirmation (MVP).
- Replace the workspace views (P2.1) or the engine (P2.2).
- Act as a generic chatbot, web-search assistant, or coding assistant.

Focus stays on reducing context reconstruction, not breadth.

## 2. Assistant Boundary

| **Context Engine owns (P2.2)** | **AI Assistant owns (P2.3)** |
|---|---|
| Relationship discovery & lifecycle | Intent understanding |
| Confidence states & scoring | Natural-language interaction |
| Context Set assembly | Interpretation & synthesis |
| Ranking | Summarisation |
| Provenance | Explanations |
| Visibility filtering | Recommendations |
| — | Action *proposals* |
| — | Conversation state |

**Consumption rule:** the assistant requests a Context Set for a resolved *(target, purpose, scope, requesting user)* and reasons only over what comes back. It never queries the raw workspace to rebuild the graph, never computes its own relationships or ranking, never bypasses or widens the visibility filter. If it needs more context it requests another purpose-scoped Set or asks the user — it does not broaden scope on its own. Connections it infers go back through the engine's suggestion/confirm path, not straight into the store.

## 3. Core User Workflows

### I1 — Resume Interrupted Work (primary)
- **Trigger:** "what was I working on?", "where did I leave off?", "what should I look at first?", "what was blocking me?"; or opening the assistant from the Resume view.
- **Behavior:** request a **Resume**-purpose Context Set for the active / most-recently-active Task(s). Answer with: current focus (latest Checkpoint), the recorded next action, blockers and `blocked by` Tasks, unresolved open questions, and a staleness note; ordered by engine ranking; citing the Checkpoint and Tasks.
- **Context required:** Resume Context Set (Checkpoint, next action, blockers, high-confidence linked Decisions/Notes), Task state, recency.
- **If no Checkpoint exists:** say so; do not invent progress; offer to help write one.

### I3 — Decision Recall (primary)
- **Trigger:** "why did we choose this?", "what alternatives did we consider?", "which decision superseded this one?"
- **Behavior:** request a **Decision-recall** Set for the named Decision or topic. Report the recorded choice, rationale, alternatives considered, `caused by` trigger, `explains` / `next action for` consequences, and the `supersedes` / `superseded by` chain. Distinguish recorded rationale (fact) from any assistant interpretation.
- **If the rationale field is empty:** state that it was not recorded; show what *is* linked (cause, consequences, author, date).

### T1 — Developer Handoff (primary)
- **Trigger:** "prepare a handoff for this task", "what does the next developer need to know?", "what context is missing?"
- **Behavior:** request a **Handoff** Context Set, visibility-filtered to the intended recipient (P2.2 §11). Produce: a draft handoff note (state, what's done, expected next, pitfalls drawn from open questions/blockers) + a structured context list. Surface the engine's "additional private context exists" sender flag and the completeness-check gaps as an explicit **"missing / to confirm"** list. Present the handoff as a **confirmable action**; never execute it.
- **Context required:** Handoff Set + completeness check + recipient scope.

### Secondary interactions (allowed; must not displace the above)
Summarise a Project/topic; find/locate an object by description; compare two Decisions or Tasks; extract candidate Tasks from a Note (as *proposed* Tasks). Same consume → reason → (propose) pattern. Not MVP-guaranteed (§13); they must never take priority over I1/I3/T1 in scope or quality.

## 4. Interaction Model

Chosen model: a **context-scoped conversational assistant** — conversational and multi-turn, but always bound to a resolved *target + purpose* so it stays grounded and bounded, not an open-ended agent roaming the workspace.

- **Conversational Q&A:** free-text questions; multi-turn follow-ups inherit the previous turn's target and scope.
- **Contextual invocation:** the assistant can be opened *from* a Project/Task/Decision; that object becomes the default target ("why this?" resolves without naming it).
- **Object references:** users can explicitly reference workspace objects; the assistant resolves each reference to a concrete object *before* reasoning and echoes which objects it used.
- **Suggested actions:** answers may end with discrete, confirmable proposed actions.
- **Explicit confirmation before mutations:** every workspace change is a proposal the user must accept; read-only answers need no confirmation.
- **Answer + grounding:** important answers show their supporting objects (§8).

UI implementation is out of scope.

---

## 5. Query Understanding

Resolved before any reasoning:

1. **Intent** — one of: Recall, Explain, Summarize, Find, Compare, Recommend, Extract, PrepareHandoff, ProposeAction; plus **Clarify** when unresolved.
2. **Target(s)** — the object(s) / Project / topic, from explicit reference, contextual invocation, or "current / last work". If unresolved and it changes the answer → ask.
3. **Purpose mapping** — intent + target → which engine Context Set purpose to request: Recall/Explain about a Decision → Decision-recall; "what was I working on" → Resume; PrepareHandoff → Handoff; Summarize/Find/Compare → a general assembled Set for the target.
4. **Scope** — time range, single object vs Project-wide, intended handoff recipient.
5. **Mutation?** — if fulfilling the request implies a workspace change, route through Action Generation (§9) as a proposal.

Ambiguity that materially changes the answer → one focused clarifying question, not several guesses answered as if certain (mirrors P2.1's ambiguity discipline). No model/provider prescribed.

---

## 6. Context Consumption

The assistant's **only** context input is the engine's response to a *(target, purpose, scope, requesting user)* request, containing:

- **Context Set** — ranked objects across layers (Direct / Recent / High-confidence; Potential only if explicitly requested).
- **Object metadata** — type, title, owner/creator/contributors, status, timestamps, home Project, relevant field content.
- **Relationship information** — typed, directional edges among included objects.
- **Confidence state** per relationship — Known / User-confirmed / Inferred-high / Weak.
- **Provenance** — relationship author or the signals behind an inferred link; object authorship.
- **Visibility constraints** — the Set is already filtered to the requesting user; the assistant must not attempt to widen it.
- **Relevant historical context** — prior Checkpoints, superseded Decisions, completed preceding Tasks (collapsed unless asked).
- **Current state** — latest Checkpoint, Task states, staleness indicator.

**When context is insufficient** (no Checkpoint for Resume, empty rationale for Recall, thin Set for Summarize): the assistant states the gap explicitly, answers only what the Set supports, and either offers an action (write a Checkpoint, record rationale) or asks the user. It must **not** fill gaps from model priors, other users' data, or general knowledge. It may request **one** additional Set (different purpose/scope); it does not loop unboundedly. The assistant never silently invents missing context.

**When the Context Engine call fails or returns nothing** (unavailable, timeout, error) — distinct from a Set that is merely thin — the assistant does not answer the substantive question at all: it reports that context could not be retrieved and offers to retry. It must not fall back to model priors, conversation history, or general knowledge to substitute for an unavailable Set.

## 7. Answer Grounding

Every answer classifies its content:

| Class | How it is presented |
|---|---|
| **Known workspace fact** (object fields, structural relationships) | Stated plainly |
| **User-confirmed relationship** | Stated plainly; may note "you linked …" |
| **Inferred relationship (high)** | "likely / appears related (inferred)" — never as fact; may invite confirmation |
| **Weak / possible relationship** | Only if the user asked to explore; always hedged and labelled |
| **Assistant interpretation** (synthesis, paraphrase, ordering) | Marked as the assistant's reading, distinct from recorded content |
| **Recommendation** | Framed as a suggestion, with its basis |
| **Unknown / unavailable** | Said plainly |

**Say "I don't know" when:** no Checkpoint / rationale / linked context supports the answer; the only support is Weak relationships; the target could not be resolved; or the needed object is outside the user's visibility — then say "not available to you", never its contents. Inference is never presented as fact (principles 5, 7).

---

## 8. Provenance / Explainability

For any answer that (a) informs a decision, (b) proposes a mutation, or (c) relies on inferred context, the assistant attaches the supporting workspace items — Decision, Note, Task, Checkpoint, Resource — and the relationships traversed, each identified well enough to open, with the confidence state shown for relationships. The user can trace an important conclusion to its sources and see which steps were inferred vs factual. Summaries cite the objects synthesised. A claim with no workspace support is not made. Citation UI is not designed here.

---

## 9. Action Generation

**Proposable actions:** create Task / Note / Idea / Decision; link objects (typed, via the engine HITL path); update a Task (status, Checkpoint fields); prepare or update a handoff; record a suggested next action on a Checkpoint.

- **Read-only reasoning** (answer, explain, summarise, compare, find, list gaps) — **no confirmation required.**
- **Proposed mutation** — every create/link/update/handoff is an explicit, editable proposal, applied only on user confirmation; attributed to the user (assistant-assisted); links go through the engine's suggestion/confirm path (P2.2 §8–9), never written as authoritative directly.
- **Automatic mutation** — **none in the MVP.** No silent writes, no auto-linking, no auto-status changes, no auto-handoff. (Conversation-derived auto-capture is a §16 open decision, default off.)

Default toward user control: the assistant drafts, the user commits.

## 10. Hallucination / Failure Handling

| Situation | Behavior |
|---|---|
| **Missing context** | State what is missing; answer only supported parts; offer an action or ask. No fabrication. |
| **Contradictory context** | Present both sources with timestamps / supersede status; do not adjudicate; flag the conflict; let the user decide. |
| **Stale context** | Lead with staleness ("latest Checkpoint is N old"); down-weight time-sensitive claims; suggest a fresh Checkpoint. |
| **Low-confidence relationships** | Exclude from the primary answer unless asked; if used, label "inferred / possible" and hedge; offer confirmation. |
| **Ambiguous question** | Ask one focused clarifying question; do not answer several guesses as if certain. |
| **Multiple valid interpretations** | State them briefly and ask which, or answer the most likely and label the assumption. |
| **Incorrect assistant reasoning** (user pushes back) | Accept the correction, re-ground from the Set, do not defend; the user's correction is authoritative for the conversation and can be captured as a Note/Decision on confirmation. |
| **Unsupported claim risk** | If it cannot be tied to a Set item or a stated inference, it is not said. |

Principle: **transparent uncertainty over fabricated certainty.**

---

## 11. Privacy and Permissions

The assistant **inherits** the Context Engine's visibility rules; it only ever receives a Context Set already scoped to the requesting user and cannot request another user's scope.

- **Private objects** — usable only in that owner's own sessions; never surfaced to anyone else, not even existence or title.
- **Shared Projects** — a teammate's assistant reasons only over shared-scope objects (plus that viewer's own private links to them).
- **Team members** — no cross-user "what is X working on" unless that context is shared; otherwise "not available to you".
- **Handoff recipients** — before acceptance, the recipient's assistant sees only what the recipient-filtered Handoff Set exposes; sender-private context appears to the *sender* only as the "additional private context exists" flag.
- **Cross-project relationships** — honored only when the user can see **both** endpoints (P2.2 §11); otherwise omitted entirely, including from summaries and counts.
- **Restricted context** — never revealed, paraphrased, or implied; the assistant says the information is not available to the user.
- **Conversation history** is per-user and inherits the same rules; a later share/unshare re-scopes what the assistant may reference going forward.

The assistant must never reveal information the requesting user is not authorized to see.

## 12. Memory / Conversation Model

| Layer | Holds | Persistence |
|---|---|---|
| **Workspace memory** | Objects + user/confirmed relationships (P2.1) | Authoritative, persistent; changed only by confirmed mutations |
| **Context Engine state** | Inferred candidates, confidence, suppressions, usage signals, Context Sets | Persistent (hybrid, P2.2 §5); not owned by the assistant |
| **Current conversation** | Resolved target/purpose/scope, turn history, the assistant's interpretations, pending proposals | Conversational state; **not** workspace context |
| **Conversation history** | Past threads, per user | Retained for continuity; not authoritative; never silently promoted to workspace objects |
| **User preferences** | Interaction defaults (verbosity, default scope) | Lightweight persistent user setting; not workspace content |

**Rules:** nothing said in a conversation becomes workspace context **except** via an explicit confirmed action (create Note/Decision/Task, add link). The assistant may use prior turns for continuity but must re-ground factual claims in a fresh Context Set, not in its own earlier answers. Conversation memory never overrides workspace or engine state. Storage implementation is not designed here.

## 13. MVP Assistant

Supports I1, I3, T1.

### MVP
- **Intents:** Recall, Explain, PrepareHandoff, plus Clarify. (Summarize / Find / Compare / Extract / Recommend deferred.)
- **Context consumption:** engine Context Sets for the three purposes (Resume, Decision-recall, Handoff); target resolution via contextual invocation + explicit reference + "current/last work".
- **Grounded answers** with the §7 content classification and §8 provenance for important answers.
- **Multi-turn follow-ups** within one resolved target/scope.
- **Action proposals** limited to: create Task; create Note/Decision from the conversation; link objects (via engine HITL); update a Task's Checkpoint/status; prepare a handoff — all confirm-before-write.
- **Handoff gap list** from the engine completeness check + private-context flag.
- **Full visibility inheritance**; per-user conversation state; "I don't know / not available to you" behavior.
- **No automatic mutations.**

### Later
- Summarize (topic/Project), Find, Compare, Extract-tasks-from-notes, Recommend / next-action generation.
- Proactive prompts (e.g. "your Checkpoint is stale") — behavioral question also raised in P2.1 §10.
- Cross-Project synthesis; richer multi-target reasoning.
- Learned user preferences; opt-in conversation-derived note drafts.
- Assistant-initiated relationship suggestions surfaced in bulk.

### Explicitly out of scope
- Being the system of record for context or relationships (principles 1–2).
- Independent workspace-graph traversal or its own retrieval bypassing the engine.
- Automatic (unconfirmed) mutations.
- External integrations, web search, code execution, generic chat / coding-assistant behavior.
- Model / provider / orchestration / tool-calling architecture (§16).
- Team analytics or cross-user activity reporting.

Do not let the MVP drift into a generic AI productivity assistant.

## 14. Evaluation Criteria

Measured eventually; no arbitrary numeric targets:

- **Answer groundedness** — share of factual claims traceable to a Context Set item.
- **Unsupported-claim rate** — claims with no workspace support (drive toward zero; hard concern for important answers).
- **Context relevance** — share of cited context the user found relevant; reliance on the top of the engine ranking.
- **Recall accuracy (I1)** — does "what was I working on" match the user's actual last state; correction rate on Resume answers.
- **Decision-recall accuracy (I3)** — rationale / alternatives / supersede chain reported correctly vs the Decision record.
- **Handoff completeness (T1)** — recipient follow-up questions per handoff; items the recipient adds right after accepting; whether the gap list caught them.
- **User correction rate** — answers or proposals corrected/rejected; trend over time.
- **Action usefulness** — proposed actions accepted vs dismissed; edits made before accepting.
- **Time saved / reconstruction effort reduced** — steps or time from question to resuming productive work vs manual navigation; qualitative "did it save the dig".
- **Uncertainty calibration** — when it said "I don't know", was context genuinely absent; when confident, was it right.
- **Privacy correctness** — zero disclosures outside the user's visibility (hard invariant).

## 15. Security / Trust Model

**Trust chain:** **User** (authenticated actor; sole authority for mutations) → **Assistant** (untrusted generator; no inherent authority; proposes only) → **Context Engine** (trusted; enforces visibility, provenance, ranking) → **Workspace** (authoritative store; changed only by confirmed user actions).

- **Permission enforcement** — performed by the engine/workspace, not the assistant; the assistant cannot request or widen scope; every engine call carries the requesting user's identity.
- **Untrusted generated output** — assistant text, and any object content it drafts from other objects' text, is treated as *data / proposal*, not instruction (prompt-injection aware); it cannot trigger writes, permission changes, or engine-config changes on its own.
- **Mutation authorization** — only an explicit user confirmation authorizes a write; proposals are inert until then; confirmed writes are attributed to the user (assistant-assisted).
- **Auditability** — every assistant-proposed, user-confirmed mutation is recorded (who, when, originating conversation, supporting context); read-only answers with their cited context may be logged for evaluation.
- **Source attribution** — important answers carry provenance (§8); recommendations carry their basis; unsupported statements are withheld.

---

## 16. Open Product / Technical Decisions

Left open until implementation requires them:

- Model selection and model routing (per-intent vs single); provider.
- Prompt / orchestration strategy; whether a tool-calling architecture is used, and its shape.
- Retrieval strategy for turning an intent into an engine request; how much of a Context Set is passed per turn (context-window budgeting).
- Streaming vs batch responses.
- Conversation persistence store, retention, cross-device sync.
- Cost / latency tradeoffs; caching of assistant answers.
- Evaluation infrastructure (offline eval sets, human review, in-product feedback capture).
- Whether and when proactive assistant prompts are appropriate (also P2.1 §10).
- Handling of very large targets (Project-wide summarise) that exceed one Context Set.
- Degree of conversation-derived auto-capture (default off; opt-in later).

No technologies are chosen here.

## Consistency with prior milestones

No contradictions. P2.2 §9 defined this boundary and required the assistant to route any discovered connection through the engine's HITL path — honored in §2 and §9. P2.1's privacy model, object set, and confirm-before-write posture are preserved. P1.2's deferred workflows (I4 next actions, I5 topic summarization) are kept as "Later", not pulled into the MVP.
