# P3.4 — AI Layer: Implementation Decisions

Consequential technical decisions taken while implementing the first AI layer.
This records **what was decided and why**, and — importantly — what was
*already* decided by P2.3 / P2.5 / P2.6 and therefore simply implemented rather
than re-opened.

Authoritative inputs: `P2.3-ai-assistant.md` (assistant behaviour, trust chain),
`P2.5-architecture-decision.md` (invariants, retrieval strategy),
`P2.6-implementation-architecture.md` (Context API, RetrievalProvider,
assistant boundary).

---

## D1 — The architecture was not re-designed. It was implemented.

The largest finding of the P3.4 reconnaissance is that **this layer was already
specified**. P2.5/P2.6 fixed the trust chain, the process boundary, the Context
API, the `RetrievalProvider` seam, the `LLMProvider` port, and the "no automatic
mutations" rule, and deliberately deferred only provider *selection*.

Building a different AI architecture would have discarded accepted decisions.
P3.4 therefore implements the specified one:

```
User → Assistant (untrusted generator, Zone B, no DB) → Context Engine (trusted) → Workspace
```

**Consequence:** the milestone's authorization guarantee is not new code — it is
the existing `VisibilityPolicy` reached through a new consumer.

---

## D2 — Semantic behaviour comes from query understanding, not a vector store

**Decision:** no embedding model, no vector database. Retrieval is the existing
Postgres FTS index behind the `RetrievalProvider` seam; "semantic" behaviour is
produced by interpreting the question into an intent + retrieval terms before
retrieval runs.

**Why:**
- P2.5 selected **lexical-only MVP retrieval** with this seam as the documented
  upgrade path, contingent on the G1–G4 quality gates. Introducing a vector
  store now contradicts an accepted decision.
- It would also create the second knowledge store the brief explicitly rules
  out, with its own consistency and authorization surface to re-secure.
- `object_fts` has been maintained by the outbox worker since P2.7 and **had
  never been read**. The correct first move is to consume what exists.

**What makes this reversible:** `ports/retrieval.ts` is storage-neutral by
construction — no SQL fragment, no query object, no driver type. A second
implementation (`InMemoryRetrievalProvider`) is kept green in the test suite
precisely so the seam cannot quietly rot. Swapping to a semantic provider
changes `adapters/retrieval/` and one wiring line.

**Cost accepted:** lexical recall is weaker than embeddings for paraphrase. The
evaluation set measures this (`index recall`), so the decision to upgrade will
be evidence-driven rather than assumed.

## D3 — Retrieval terms are OR-ed, not AND-ed

**Decision:** free text is reduced to terms and combined with `or` before
`websearch_to_tsquery`.

**Why:** found by running the real system, not by a test. `websearch_to_tsquery`
ANDs bare terms, so "why did we choose token bucket?" → `choose token bucket`
required *all three* words, and the note actually titled "Chose token-bucket
over sliding-window" did not match at all. The pipeline then fell back to
recency and answered with the most recent note — confidently, and about the
wrong thing.

`ts_rank` does the discriminating instead: documents matching more terms rank
higher, partial matches stay reachable.

**Cost accepted:** phrase queries lose exactness. Recall matters more for
questions.

**Regression guard:** the evaluation set now measures **index recall**
separately from citation. The original eval scored this case as passing because
the right note was cited — via the recency fallback — which hid the defect.
Measuring the two separately is what makes the metric honest.

## D4 — Provider selection: deterministic fake by default, one real adapter opt-in

**Decision:** `LLMProvider` port; `FakeLLMProvider` is the default; an Anthropic
adapter activates only when `ANTHROPIC_API_KEY` is set. No new dependency (the
adapter uses global `fetch`).

**Why:** P2.6 §14 fixed the port and deferred selection. Assuming a provider
would bake a vendor into the architecture the brief forbids. More practically:
every property worth asserting — authorization, grounding, provenance, refusal,
inert proposals — is a property of the **pipeline**, not the model. Making the
default deterministic is what allows those to be tested at all.

**Consequence:** swapping providers must not change the authorization,
provenance or grounding columns of the evaluation set. Those are pipeline
guarantees.

---

## D5 — The model is untrusted, so its output is re-validated

**Decision:** citations and task proposals returned by the model are checked
against the evidence actually supplied before anything reaches the UI.

- A cited ref that is not in the evidence set is **dropped** — a hallucinated
  citation cannot become a citation.
- A proposal naming a source that is not in the evidence set keeps its text but
  **loses the attribution** rather than carrying a false provenance claim.
- An answer with evidence but no surviving citation is marked **ungrounded** in
  the UI rather than presented as fact.

**Why:** P2.3 §7/§10 require grounding classification and forbid unsupported
claims. Prompting alone cannot guarantee this; validation can.

---

## D6 — Scope of the Context Engine implemented here

**Decision:** `direct` / `recent` / `high_confidence` layers over a **one-hop**
expansion, with a deterministic total order and per-layer caps.

Deferred, deliberately: the 2-hop recursive CTE, `ranking_weight_set` rows,
suggestion-derived candidates, `indirect` / `historical` / `potential` layers,
and the handoff purpose. None is required by the P3.4 slice, and the brief rules
out speculative infrastructure.

**Kept from the specification because it is load-bearing:**
- visibility composed into every step (no step sees unfiltered data);
- `canSee` re-check on every retrieval hit (defence in depth);
- `Unavailable(reason)` as a result **distinct** from an empty set — the
  assistant may say "I found nothing" for the latter and must refuse for the
  former;
- a deterministic total order, so the same inputs give the same set.

### D6.1 — The score ladder

Ranking order was corrected during evaluation:

```
explicit target 1.0 > retrieval match 0.7+ > recent work 0.5 > related 0.4/0.25 > containing project 0.2
```

Originally the containing project outranked recent work, so "what was I working
on?" answered with the *project* rather than the work. The rule now encoded:
**the thing you asked about outranks the thing that merely contains it.**

## D7 — Task extraction is a proposal, never a write

**Decision:** the assistant returns inert proposals. Creation happens in the
**core**, through the ordinary authenticated write path, initiated by the user,
attributed to the user.

- The assistant has no write endpoint and no datastore credential — asserted by
  an architecture test that walks its module graph (INV-4).
- A created task records `createdVia: assistant_proposal` as an *attribute* and
  links to its source with a real `derived_from` relationship (INV-2) — so the
  provenance of an AI-assisted creation survives, without misattributing
  authorship to the model.

---

## D8 — Two credentials on the Context API

Implemented as specified (P2.6 §14.1): a **service token** authenticates the
assistant as a *caller*; the **end-user credential** is relayed verbatim and
validated by the core, which derives the principal from it alone.

A call with only a service token is rejected — there is no user to act for.
A principal in the body or an assistant-set header is ignored. Both are tested.

**Consequence:** the assistant cannot request another user's context, because it
holds no credential for another user.

## Open / deferred

- **G1–G4 gate instrumentation** (P2.5 §13.4) — the evaluation set is the first
  concrete measurement surface; wiring it to persisted telemetry is later work.
- **Conversation store** (P2.6 §7.3) — multi-turn continuity is not in this
  slice; each turn re-grounds from a fresh ContextSet, which P2.3 §12 requires
  anyway.
- **Handoff purpose**, 2-hop assembly, ranking weight-set rows.
- **Provider hardening** — retries/backoff beyond a single timeout, and a
  redaction/consent point at the egress boundary (P2.5 §22).
