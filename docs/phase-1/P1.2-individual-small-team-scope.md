# P1.2 — Individual + Small-Team Scope

Decision-support document. Establishes candidate workflows and product scope around the P1.1 problem (**loss of connected developer context**). Not implementation, architecture, technology, schema, UI, API, AI design, or the P5.3 "killer workflow".

Context: `Claude_Project_Blueprint.md`, `docs/phase-1/P1.1-problem-definition.md`.

---

## 1. Scope Objective

Define the highest-value **workflows** the product must serve for (a) the individual developer and (b) the small development team, so later phases design and validate against a bounded set rather than the full blueprint surface.

A *workflow* here = a recurring situation with a user, a trigger, a required set of connected context, and a desired outcome. Enabling *capabilities* (capture, connection) are called out separately: they have no standalone payoff but every workflow depends on them.

Evaluation axes applied to each candidate: user · trigger · current problem · desired outcome · frequency · pain severity · context required · why existing tools fail · product value · link to P1.1 · disposition (MVP / Deferred / Rejected).

---

## 2. Individual Developer Workflows

### Enabling capability E1 — Frictionless in-flow capture
- **User:** individual developer. **Trigger:** a note/idea/decision/link arises while working. **Current problem:** capturing it means leaving flow and choosing a tool; the connection to current work is lost. **Desired outcome:** capture in one step, auto-attached to the active piece of work. **Frequency:** many times/day. **Severity:** medium per event, high cumulative. **Context required:** what the developer is currently working on. **Why tools fail:** each capture tool is a separate silo with no notion of "current work". **Value:** without this there is no context layer to connect. **P1.1 link:** addresses the *vertical* fragmentation axis (item recorded, rationale/links not). **Disposition:** MVP (enabler).

### Enabling capability E2 — Assisted connection between items
- **User:** individual developer. **Trigger:** two or more captured items are related (task ↔ project ↔ decision ↔ notes ↔ next action). **Current problem:** linking is manual, cross-tool, and decays, so it does not happen. **Desired outcome:** the system proposes/maintains typed links so the relationship graph actually exists. **Frequency:** continuous, mostly passive. **Severity:** high (this is the core gap). **Context required:** all captured items + their types. **Why tools fail:** none maintain typed relationships across item types and tools. **Value:** turns a pile of items into a navigable graph; the product's core differentiator. **P1.1 link:** directly addresses the central problem — relationships never externalized. **Disposition:** MVP (enabler); scope = assisted/suggested linking, not a guarantee of full automation.

### I1 — Resume interrupted work
- **User:** individual. **Trigger:** returning after a context switch (meeting, next day, task swap). **Current problem:** manually reloading "where was I, why, what's next" from scattered artifacts + fading memory. **Desired outcome:** one view of the active work's state, rationale, and next action. **Frequency:** daily, often multiple times. **Severity:** medium–high per event; dominant cumulative cost. **Context required:** current task, its project, related decisions/notes, last action, intended next action. **Why tools fail:** state is split across issue tracker, notes, chat, editor, memory; none assembles it. **Value:** highest-frequency individual payoff; visible and demonstrable. **P1.1 link:** the *temporal* fragmentation axis. **Disposition:** MVP — primary individual workflow.

### I2 — Recover context on a dormant/old project
- **User:** individual. **Trigger:** returning to a project after weeks/months. **Current problem:** the connective picture is gone; only raw artifacts remain. **Desired outcome:** navigable map of the project's decisions, state, and open threads. **Frequency:** occasional. **Severity:** high per event. **Context required:** project-scoped decisions, notes, tasks, history. **Why tools fail:** same as I1 at longer range. **Value:** high but infrequent; runs on the *same machinery* as I1 + E2 with no extra scope. **P1.1 link:** temporal fragmentation, long range. **Disposition:** Deferred (near-term) — emerges from I1 + E2, no dedicated MVP work.

### I3 — Decision recall ("why did I choose X?")
- **User:** individual. **Trigger:** encountering or revisiting a past technical decision. **Current problem:** rationale was in chat / in head / never written; irrecoverable. **Desired outcome:** retrieve the decision with its rationale, alternatives, and triggering context. **Frequency:** medium. **Severity:** high per event (wrong assumptions cause rework). **Context required:** decision records linked to their cause (issue/idea) and consequences (tasks/code). **Why tools fail:** decisions are unstructured and unlinked; chat is not practically searchable by relationship. **Value:** concrete, demonstrable, flagship blueprint example. **P1.1 link:** vertical fragmentation (item vs rationale). **Disposition:** MVP — secondary individual payoff, depends on E1+E2.

### I4 — Turn accumulated context into next actions
- **User:** individual. **Trigger:** "what should I work on next?" / "turn these notes into tasks". **Current problem:** next actions are implicit in scattered notes. **Desired outcome:** proposed prioritized actions derived from the context graph. **Frequency:** medium. **Severity:** low–medium. **Context required:** a mature, well-connected graph across projects. **Why tools fail:** no tool holds enough connected context to reason over. **Value:** high once the graph is rich; low before then. **P1.1 link:** consumes connected context; does not itself solve fragmentation. **Disposition:** Deferred — depends on graph maturity + reasoning layer.

### I5 — Topic summarization ("summarize everything about auth")
- **User:** individual. **Trigger:** need a cross-project view of one topic. **Current problem:** topic material is spread across items and tools. **Desired outcome:** synthesized summary with links to sources. **Frequency:** low–medium. **Severity:** medium. **Context required:** graph + retrieval + synthesis. **Why tools fail:** no connected corpus to summarize. **Value:** useful, not foundational. **P1.1 link:** downstream consumer. **Disposition:** Deferred.

## 3. Small-Team Workflows

### T1 — Developer handoff
- **User:** two developers (giver + receiver), small team. **Trigger:** reassigning a task/project (review, PTO, load-balancing, "can you pick this up"). **Current problem:** connective context lives only in the giver's head; receiver reconstructs it by interrogating the giver or guessing. **Desired outcome:** transfer the work item with its state, rationale, decisions, and next action intact. **Frequency:** frequent in small teams (weekly+). **Severity:** high — lost context here causes rework and mistakes. **Context required:** the item's full connected context (same set as I1) made legible to another person. **Why tools fail:** issue trackers hand over a title + comments, not the reasoning graph; chat history is not transferable context. **Value:** strongest team payoff; reuses I1 machinery pointed at another user. **P1.1 link:** the reconstruction cost at a *person* boundary instead of a *time* boundary. **Disposition:** MVP — primary team workflow (thin: relies on individuals having captured).

### T2 — Shared decision understanding
- **User:** any teammate. **Trigger:** encountering a decision they did not make. **Current problem:** must find and ask the author. **Desired outcome:** self-serve the decision + rationale. **Frequency:** medium. **Severity:** medium–high. **Context required:** shared, linked decision records (I3 made visible to the team). **Why tools fail:** rationale is undocumented or buried in DMs. **Value:** high, cheap once I3 + sharing exist. **P1.1 link:** vertical fragmentation, team-visible. **Disposition:** Deferred (near-term) — first follow-on after MVP; near-trivial given I3 + T1.

### T3 — Onboarding / re-onboarding
- **User:** new or returning developer. **Trigger:** joining a project. **Current problem:** starts from scattered artifacts with no map; senior devs spend hours narrating context. **Desired outcome:** navigable project context map. **Frequency:** low. **Severity:** high per event. **Context required:** project-scoped graph (same as I2) shared. **Why tools fail:** README + tribal knowledge; nothing captures the "why" graph. **Value:** high but infrequent; falls out of I2 + T1 + sharing. **P1.1 link:** temporal + person fragmentation combined. **Disposition:** Deferred.

### T4 — Avoid duplicated work
- **User:** developer about to start something. **Trigger:** beginning investigation/implementation. **Current problem:** a teammate may have already explored or decided this; no way to know. **Desired outcome:** surface prior related work/decisions before starting. **Frequency:** medium. **Severity:** medium–high when it hits. **Context required:** cross-member discovery/search over a well-populated shared graph. **Why tools fail:** knowledge is siloed per person. **Value:** high, but requires broad capture discipline + discovery capability. **Disposition:** Deferred — harder, depends on adoption depth.

### T5 — Recover team project context
- **User:** team collectively. **Trigger:** "what is the state of project X and why". **Current problem:** no shared current picture. **Desired outcome:** shared project state + rationale view. **Context required:** project graph, shared. **Disposition:** Deferred — same machinery as I2/T3 at project granularity.

### Enabling capability E3 — Share context without manual reconstruction
- The mechanism under T1/T2/T3: expose the relevant subset of one person's connected context to teammates without them rebuilding it. Not a standalone workflow; folds into MVP as the sharing dimension of E2 + T1. **Disposition:** MVP (enabler, minimal: per-item/per-project sharing).

## 5. Shared Core Problem

Every ranked workflow is the same event: **a context boundary forces someone to reconstruct connective reasoning that was never externalized** (P1.1).

- **I1** crosses a *time* boundary within one person.
- **T1** crosses a *person* boundary within one team.
- I2/T3 cross a *long time* boundary; T2/T4/T5 cross person boundaries at other granularities.

Team workflows are the individual problem projected across people instead of across time. Solving the individual reconstruction problem produces most of the team machinery for free; the reverse does not hold.

---

## 6. Individual vs Team Priority

**If the two conflict, the individual workflow (I1) takes priority.**

Rationale:
1. **Dependency direction:** T1 can only transfer context that an individual captured and connected. No individual loop → nothing to hand off.
2. **P1.1 user ranking:** individual is the primary target user; small team is secondary and derived.
3. **Adoption:** solo value must land first; a developer adopts for personal payoff before a team standardizes on it.
4. **Reuse:** the team layer is largely I1's machinery pointed at a second user + a sharing boundary, so prioritizing I1 does not strand the team.

Team scope is therefore built as a thin layer on the individual loop, not as a parallel track.

---

## 7. MVP Candidates

- **E1** — frictionless in-flow capture, auto-attached to current work.
- **E2** — assisted typed connection between captured items (suggested links; no full-automation guarantee).
- **E3** — minimal context sharing (per item / per project).
- **I1** — resume interrupted work: one assembled view of active work's state, rationale, next action.
- **I3** — decision recall: decision records linked to cause and consequences.
- **T1** — developer handoff: transfer a work item with its connected context legible to the receiver.

This set delivers one complete individual loop (Capture → Connect → Understand → Act at a basic level) plus the single strongest team workflow reusing it.

---

## 8. Deferred / Rejected Workflows

**Deferred (near-term, cheap follow-ons):** T2 shared decision understanding, I2 dormant-project recovery.

**Deferred (later, need graph maturity / adoption depth / reasoning or discovery layers):** I4 next actions, I5 topic summarization, T3 onboarding, T4 avoid duplicated work, T5 team project recovery.

**Rejected (out of scope — would turn the product into generic productivity/team software):**
- Generic task/project management (boards, sprints, estimates, burndown).
- Team chat / messaging.
- Generic wiki / PKM note-taking as an end in itself.
- Calendar, standup automation, status reporting, time tracking.
- Cross-org / enterprise knowledge management.
- Non-developer knowledge work.

---

## 9. Open Questions for Later Validation

1. **Automation bar for E2:** is suggested/assisted linking sufficient, or must connection be automatic to deliver value?
2. **Adoption threshold:** minimum capture discipline before the context layer pays off — and how to make E1 low-friction enough to reach it.
3. **Wedge choice:** is I1 (resume) or I3 (decision recall) the more compelling entry point for solo adoption?
4. **Sharing model for teams:** context shared by default vs. opt-in per item/project.
5. **Handoff dependency:** does T1 deliver validated value with manual capture only, or does it require external-tool integration (e.g. GitHub) to be credible?
6. **Context unit granularity:** is the primary unit a task, a project, or a work session — and does it differ for I1 vs T1?
7. **Individual→team transition:** what triggers a solo user's context becoming team context without a disruptive migration?

(These feed P5 validation. P1.2 does not answer them and does not select the P5.3 killer workflow.)
