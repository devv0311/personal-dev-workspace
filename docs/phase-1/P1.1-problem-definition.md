# P1.1 — Problem Definition

Decision-support document. Foundation for subsequent product decisions. Not a feature spec, solution design, architecture, or technology selection.

Source of authority: `Claude_Project_Blueprint.md`.

---

## 1. Problem Statement

A developer's working knowledge — the ideas, tasks, notes, decisions, project context, and learning that explain *what they are doing and why* — is externalized as isolated items in tool-shaped silos, while the **relationships between those items are never externalized at all**. Those relationships (this task belongs to that project; this note explains that decision; this decision was caused by that issue) live only in the developer's short-term memory.

When that mental context decays — through a context switch, the passage of time, or a handoff to a teammate — the individual artifacts survive but become hard to navigate, because nothing recorded how they connect. The developer (or their teammate) then pays a recurring **reconstruction cost**: re-reading scattered material and re-deriving the connective reasoning that was already worked out once.

The fundamental problem is **the loss of connected context**, not the absence of a place to store items. Existing tools already store items well. None of them maintain the typed connections *between* items across tool boundaries and over time.

---

## 2. Primary Target User

**The individual developer** (solo developer, and the individual contributor working within a team).

Rationale:
- They personally bear the daily reconstruction cost every time they resume interrupted work or return to an older project.
- They are the atomic unit of capture: connected context only exists if an individual records it as they work.
- The blueprint's core loop (Capture → Connect → Understand → Act) is a single-person loop before it is a team loop.

---

## 3. Secondary Target User

**Small development teams** (roughly 2–10 developers).

Justified because:
- The blueprint explicitly requires the system to work for small teams, not only solo developers.
- Handoffs multiply the same underlying problem: when connective context lives only in one person's head, teammates cannot recover *why* a decision was made or *what* a project's current state is, producing lost decisions, duplicated work, and slow onboarding.
- It is *secondary*, not co-primary, because team value is derived: a shared context layer is only as good as the individual capture habits feeding it. Solve the individual problem first and the team problem becomes tractable; the reverse is not true.

---

## 4. Problem Context

Developer knowledge is fragmented along three distinct axes:

- **Horizontal (across tools):** related information for one piece of work is split across an issue tracker, a notes app, chat history, design docs, a code host, and the developer's memory. Each tool is optimized to store and retrieve one *type* of item. No tool owns the cross-type links.
- **Vertical (item vs. rationale):** an artifact is recorded, but the reasoning that gives it meaning is not. A merged PR exists; the trade-off discussion that justified it does not. A task exists; the idea it came from does not.
- **Temporal (context decay):** the connective context is obvious and cheap to hold *while the work is active*, and expensive or impossible to reconstruct weeks later. The value of a captured link is highest precisely when it is least likely to have been written down.

Because the relationship graph is never externalized, it cannot be searched, shared, inherited by a teammate, or handed to an assistant. Every consumer of that context has to rebuild it from raw items.

---

## 5. Core Pain Points

1. **Resume cost after interruption** — returning to work after a context switch requires manually reloading "where was I and why".
2. **Decision amnesia** — the rationale behind past technical decisions is lost; questions like "why did we choose X?" have no recorded answer.
3. **Manual, decaying linking** — connecting related items (issue ↔ project ↔ decision ↔ notes ↔ next action) is manual, tedious, and goes stale, so it mostly does not happen.
4. **Retrieval by location, not by relationship** — finding information depends on remembering *which tool* it is in, not on how it relates to the current task.
5. **Non-transferable context** — a teammate cannot inherit the connective picture; it never left the original developer's head.
6. **Onboarding and re-onboarding friction** — new teammates, and the original developer returning to a dormant project, both start from scattered artifacts with no map.
7. **Assistants without memory** — AI tools cannot meaningfully answer "what was I working on?" or "summarize everything about auth" because no persistent, connected context is available to them.

---

## 6. What Existing Tools Fail to Solve

- **Note / PKM tools (e.g. Notion, Obsidian):** store items and support manual links, but linking is effortful, confined to that tool, and not maintained as work evolves. They do not ingest or relate developer activity from other systems.
- **Issue trackers / project tools:** model tasks and status well, but hold only one slice of context and treat notes, ideas, decisions, and rationale as second-class or external.
- **Chat / communication tools:** where much decision rationale actually happens, but it is unstructured, unsearchable in practice, and never linked to the project or task it concerns.
- **Code hosts / IDEs:** hold code and its history, but not the surrounding ideas, decisions, and project context that explain it.
- **General AI assistants:** lack persistent, personal, connected context about the developer's own work, so they cannot recall history or explain past decisions.

The common gap: each tool captures items of one type; **none maintains typed relationships across types, across tools, and across time.** That connective layer is exactly what is missing.

---

## 7. Scope Boundary / What This Problem Definition Does NOT Claim

- It does **not** claim the problem is primarily a *search* or *storage* problem. Storage exists; connection is missing.
- It does **not** claim existing tools should be replaced. The problem concerns the missing layer *between* them.
- It does **not** prescribe a solution, feature set, data model, architecture, or technology stack.
- It does **not** assert that team collaboration is the primary use case; the individual is primary, the team is secondary.
- It does **not** address non-developer knowledge work, general enterprise knowledge management, or end-user-facing product documentation.
- It does **not** assume AI is required to solve the problem; AI is one possible consumer of connected context, not part of the problem statement.
- It does **not** define success metrics, validation methodology, or the "killer workflow" — those belong to later roadmap phases.
- It does **not** execute or pre-empt P1.2 (individual + small-team scope and core workflows) or any later phase.
