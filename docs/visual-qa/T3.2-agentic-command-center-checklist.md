## 2. Central command centre

- [x] A prominent central ring with a core in the middle is the OS resting state.
- [x] The ring carries **only real capabilities** — `/capture`, `/ask`,
      `/summarize`, `/extract-tasks`, Connect, Search — each wired to a handler
      the shell already has. The ring is sized by that list; it is not padded.
- [x] Reference density is reproduced with **non-semantic** geometry: a faceted
      wireframe enclosure, three orbital guides, twelve spokes, a 72-tick ring,
      a dashed outer boundary, hollow inter-badge markers and hairlines, and a
      720-particle mass. None carries an id, a count, a label or a handler.
- [x] Dark canvas; restrained orange / cyan / purple / amber accents; localized
      bloom; strong spatial depth; the centre is the largest single surface.

## 3. Core and the transition

- [x] The core carries the DEVWORKSPACE identity mark and its **real** size
      (`18 OBJECTS · 3 PROJECTS`), which agrees with the field readout
      (`15 CAPTURES · 3 PROJECTS · 21 LINKS`) and with Project Pulse.
- [x] `CLICK TO OPEN SECOND BRAIN` sits under the core, above a hairline, in
      tier-4 type — present and clearly secondary.
- [x] The core is clickable and keyboard-activatable (`role="button"`,
      `tabindex="0"`, Enter/Space).
- [x] Clicking it changes **place**: OS command view → Second Brain, full canvas,
      rails withdrawn.
- [x] `← BACK TO DEVWORKSPACE` is always on screen; Escape also returns.

## 4. Second-Brain ring system

- [x] Concentric rings, core outward: **core** (workspace) → **capabilities**
      (inner) → **projects / domains** → **context rings** (fill outward) →
      **outer system boundary**.
- [x] Objects on the rings are the same objects the OS view, search, the
      inspector and Project Pulse hold — one payload, two projections
      (asserted in `test/graph-model.test.js`).
- [x] The capability ring is drawn by the view, never as a graph object: it has
      no id, never appears in search, never opens the inspector.
- [x] Ring annotations state each ring's **real** name and **real** count. The
      Inbox ring is empty and says `0` rather than being hidden or filled.
- [x] No taxonomy was invented: no Applications / Routines / Memory object
      classes exist in the model and none are drawn.
- [x] Circular tracks, radial spokes, luminous nodes, fine relationship lines,
      restrained glow, a dense central memory mass, technical labels.
- [x] Not a force graph — the layout is deterministic and positional.

## 5. Colour semantics

- [x] Orange → core, capabilities, action. Cyan → projects (domains).
      Purple → captured context. Amber → tasks (temporal).
- [x] Colour never carries a meaning alone: every class is also stated by the
      node's label, its ring annotation and the inspector's type line.
- [x] Saturation is confined to those four roles; everything else is greyscale.

## Known limitations

1. **Email and Routines are visual surfaces only.** Both are required by the
   composition and neither has a backing system, so both are rendered in an
   explicitly stated not-connected / offline state. They will carry real data
   only when a mail integration and a scheduler exist.
2. **The assistant runs its development stub locally.** Cards therefore read
   `assistant · dev stub`. Against a real provider the same code path prints the
   provider and the model it reports.
3. **The header's search and Second Brain controls are hidden below 720 px.**
   Both remain reachable from Micro Apps, and `/` still opens search.
4. **Team surface is membership only.** Switching the dev principal to a member
   who owns nothing correctly yields an empty workspace — that is
   deny-by-default working, not a defect.
